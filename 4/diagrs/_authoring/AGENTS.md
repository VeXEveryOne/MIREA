# Правила OmniNotation

Актуализировано по указаниям пользователя 9 сентября 2026 года.

- Для всех нотаций используется собственный общий текстовый язык. Основа — простота DFD, а не сторонние языки разметки.
- Общий хост — `NotationEditor`, единственное ReactFlow-полотно — `DiagramCanvas`. Новые нотации подключать к ним. Канонический каталог — `src/notations/registry.ts`; списки для подсказок, палитр и преобразований выводить из него, не дублировать.
- Для всех нотаций используется один общий хост визуального редактора и единый реестр нотационных адаптеров. Адаптер задаёт модель, проверку, команды, палитру и отрисовку конкретной нотации; UI не должен создавать независимые несвязанные редакторы. Общая оболочка не смешивает семантику: активный адаптер и автокомплит показывают только типы и параметры своей нотации (в DFD нет BPMN-элементов и наоборот; то же правило действует для IDEF0 и UML).
- Формат элемента: `тип id название ключ=значение`. Для стрелки IDEF0 допускается флаг видимости перед названием: `arrow id -h название ключ=значение`. Один элемент на строку; поля и необязательные параметры разделяются пробелами. Без `\`, запятых, скобок и `;`. Короткие значения без кавычек, многословные/специальные и пустые — в двойных кавычках. Заголовок первой строкой: `нотация id название`. Точные правила NS-TEXT-2 — в docs/reference/LANGUAGE.md.
- Примеры: `process checkOrder "Проверить заказ" type=user`, `flow request Заявка from=start to=checkOrder`.
- Семантика типов и набор допустимых параметров зависят от нотации; порядок полей, комментарии, строки и принципы редактирования одинаковы.
- XML ЗАПРЕЩЁН как язык диаграмм, формат проекта, промежуточное представление приложения, способ импорта/экспорта и содержимое примеров. Не возвращать XML/BPMN XML в редактор или пользовательские сценарии и не вызывать XML-парсеры/сериализаторы в коде приложения. Не заменять XML другим сторонним сложным языком.
- Использовать единое расширение `.omni` для собственных версионируемых JSON-контейнеров: поле `notation` выбирает модель, внутри хранятся собственный исходный текст, черновик и отдельное расположение элементов. Старые `.nsdfd`, `.nsidef0`, `.nsuml`, `.nsbpmn` допускаются только для чтения и миграции существующих файлов; новые файлы и примеры получают `.omni`.
- По указанию пользователя от 09.09.2026 BPMN использует собственный редактор: команды, SVG-фигуры, свойства и синхронизация в коде проекта; React Flow предоставляет полотно. `bpmn-js` удалён, не возвращать его в качестве редактора. `bpmn-moddle` оставлен только для дескрипторов и восстановления собственного JSON-графа. XML API по-прежнему запрещены.
- При ошибочном коде сохранять черновик и последнюю корректную модель. Не менять модель частично и не терять скрытые свойства при преобразованиях.
- BPMN развивать по чеклисту из `C:\Users\Savva\Documents\Заметки\OmniNotation\Таблица с нотациями.md`. Локальный статус вести в `docs/status/BPMN_CHECKLIST.md`; не выдавать подключение библиотеки за полную реализацию стандарта.
- Для BPMN читать `docs/BPMN_2_RULES.md`: проверенный профиль, первоисточник, неоднозначности и этапы. Историческая таблица не отменяет уточнения OMG. Разделять блокирующую семантическую ошибку и предупреждение о незавершённом построении.
- По указанию пользователя от 18.09.2026 тестовые исходники и инфраструктура удалены. Не создавать и не запускать unit-, Electron E2E- и другие автоматизированные тесты до явного обратного указания пользователя. Проверка типов и сборка допускаются; не выдавать их за тестирование поведения.
- Действующие пользовательские указания о собственном языке и запрете XML имеют приоритет над историческим заданием в `docs/archive/SPEC.md` и старыми планами.
- Статический текст и элементы управления оболочки не должны выделяться как текст: общий контейнер задаёт `user-select: none`. Выделение разрешено только в фактических областях редактирования — `input`, `textarea`, `[contenteditable=true]`, поле переименования файла и Monaco. `Ctrl/Cmd+A` вне такой области поглощается без выделения интерфейса или объектов диаграммы; внутри области выделяет только редактируемый текст. Новые UI-компоненты наследуют общий запрет и не расширяют исключения без отдельного пользовательского требования.

## Постоянная база знаний (9 сентября 2026)

- Перед изменением логики прочитать `docs/codebase/README.md`, соответствующий раздел `module-catalog.md` и реальный исходник. Для языка/синхронизации читать `code-to-diagram.md`; для ошибок/сохранения — `validation-handbook.md`.
- Правила и источники нотаций собраны в `docs/NOTATION_RULES.md`. Различать действующие пользовательские требования, стандарт, локальный профиль, фактическое покрытие и предложения. Не объявлять цели реализованными.
- Для семантики DFD/IDEF0/BPMN/UML использовать `.agents/skills/omninotation-notations/SKILL.md`; для собственного языка и round-trip — `.agents/skills/omninotation-code-model/SKILL.md`. Для Electron, платформенных команд, восстановления и сборок использовать `.agents/skills/omninotation-desktop/SKILL.md`. Читать применимый навык перед задачей, не загружать остальные без необходимости.
- После изменения поведения обновить соответствующий каталог/правила и `docs/codebase/logic-changelog.md`. По указанию пользователя от 24.09.2026 после каждого изменения файлов сразу обновлять карту: `node scripts/generate-project-map.mjs`, не откладывая до завершения задачи. Генерируемые файлы самой карты не требуют повторного запуска по кругу. Карта — навигация, исходники — свидетельство поведения.
- `src/language/generated/` изменяется через Langium generate; грамматики править в `.langium`. Новые примеры писать только на общем собственном языке.
- `agent.md` — справочный указатель. Канонические инструкции находятся здесь, в `AGENTS.md`; не вести две независимые копии правил.
- Справочник возможностей и использования для AI-агентов — `docs/guides/AI_AGENT_GUIDE.md`. При изменении доступных функций, команд или форматов обновлять соответствующий раздел вместе с кодом; генератор карты не обновляет смысловое описание возможностей.
- По указанию пользователя от 04.10.2026 при каждом изменении проекта обязательно проверять и актуализировать правила построения схем для нейросетей. Изменения типов, параметров, ссылок, владельцев, семантики, языка, форматов и доступных команд отражать в соответствующих документах-источниках (`docs/reference/LANGUAGE.md`, `docs/NOTATION_RULES.md`, нотационные правила и руководства) вместе с кодом. Если изменение не влияет на построение, явно фиксировать это в записи задачи в `docs/codebase/logic-changelog.md`, не придумывая новых правил. После обновления источников и перед передачей результата всегда пересобирать единый файл `docs/guides/AI_NOTATION_INSTRUCTIONS.md` командой `npx tsx scripts/generate-notation-instructions.ts`, затем сразу обновлять карту. Единый файл содержит инструкции для всех зарегистрированных нотаций, каталог из реестра и примеры; вручную его не редактировать. Генератор собирает пакет, но не заменяет смысловое обновление правил.

## Работа двух разработчиков

- Работать в текущей ветке и существующей папке проекта. Не создавать для задач новые ветки, worktree, клоны или отдельные копии/каталоги проекта. Ветки при необходимости создают сами пользователи. Создание или переключение ветки/рабочего каталога агентом допустимо только по отдельному явному поручению пользователя; новая задача сама по себе таким поручением не является.
- Перед изменениями проверить status и текущую ветку. Если смысл запроса, нужная ветка или рабочая папка непонятны, задать пользователю уточняющий вопрос до зависимых действий. Не заменять уточнение созданием ветки или копии проекта. Подробности — в `docs/COLLABORATION.md`.
- Не менять checkout другого разработчика и не включать его изменения в свою задачу. Общие грамматики, контейнеры и App.tsx согласовывать как точки пересечения.
- Worktree не изолирует userData Electron. Не запускать два экземпляра для независимых проверок восстановления без отдельной настройки профилей.
- Проверять diff перед передачей. Публикация ветки и интеграция выполняются в рамках пользовательской задачи; не переписывать общую историю и не удалять worktree с несохранённой работой.

## Расположение файлов

- Сборка приложения включает один переносимый AI-навык для всех зарегистрированных нотаций: `scripts/build-ai-skill.ts` собирает `dist/ai-skill/omninotation-diagrams` из шаблона SKILL.md и генерируемого единого справочника. Не создавать независимые копии семантических правил в шаблоне. Forge доставляет навык вне app.asar в resources/ai-skill; рабочая docs целиком не включается в выпуск. Build очищает только проверенную генерируемую dist, не исходники, out или release-assets. Отдельный ZIP навыка не требуется: он входит в сборки приложения.

- В корне оставлять только точки входа и метаданные: `README.md`, `AGENTS.md`, справочный `agent.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `package.json`, `package-lock.json`, `index.html`, `tsconfig.json`, `langium-config.json` и служебные dotfiles. TypeScript и Langium используют корневые конфигурации для стандартного обнаружения и разрешения путей.
- `config/` — конфигурации Vite и Electron Forge. Их пути явно указаны в npm scripts; команды запускать из корня текущего проекта. При переносе учитывать базу относительных путей конкретного инструмента.
- `src/` — код приложения: `main/` — Electron и IPC, `ui/` — интерфейс, `domain/` — модель, `language/` — общий язык, `notations/<notation>/` — адаптеры нотаций, `validation/` — проверки, `persistence/` — сохранение. Новый файл размещать рядом с владельцем соответствующей ответственности.
- `scripts/` — команды разработки, генерации и выпуска; `examples/` — примеры собственных JSON-контейнеров. Каталога тестов нет и до обратного указания пользователя создавать его нельзя.
- Документация — в `docs/`: `guides/` — руководства пользователя, `reference/` — язык и справочные материалы, `development/` — зависимости и разработка, `status/` — покрытие, чеклисты и отчёты, `plans/` — актуальные планы, `archive/` — исторические задания. `codebase/` — база знаний и генерируемая карта, `releases/` — заметки выпусков, `screenshots/` — изображения. Общепроектные правила и процессы остаются непосредственно в `docs/`; указатель — `docs/README.md`.
- `.github/` — workflows и шаблоны GitHub; `.agents/skills/` — проектные навыки. Не создавать дубликаты инструкций и документов в корне.
- `node_modules/`, `dist/`, `out/`, `release-assets/` и `.tools/` — локальные зависимости и артефакты, исключённые из Git. Временные материалы не складывать в корень и не коммитить. Отдельные папки проекта и worktree самостоятельно не создавать; правила — в `docs/COLLABORATION.md`.
- При переносе обновлять относительные ссылки, импорты, npm scripts, CI и ресурсы упаковки; затем перегенерировать карту. Новый корневой файл допустим только при технической необходимости, причину фиксировать здесь.
