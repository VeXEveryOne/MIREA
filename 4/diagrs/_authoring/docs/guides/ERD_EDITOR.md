# ERD — сущности и таблицы

ERD описывает **данные, их атрибуты, ключи и отношения**. В одном проекте можно иметь концептуальный, логический и физический листы с общими сущностями. Основные действия — в [общем руководстве](USER_GUIDE.md).

## Выбрать уровень модели

| Лист | Что строить |
| --- | --- |
| Концептуальный | Сущности, атрибуты и бинарные отношения Чена: прямоугольники, овалы, ромбы |
| Логический | Структуру сущностей, атрибуты, ключи и кратности без привязки к конкретной БД |
| Физический | Таблицы, SQL-имена/типы, PK/UQ/FK, индексы, проверки, последовательности |

Новая сущность — объект модели. Показав её на другом листе, вы получаете другой вид того же объекта. Скрытие овала атрибута не удаляет колонку. Название для человека и SQL-имя могут различаться.

## Пример: покупатели и заказы

1. Создайте ERD с логическим или физическим листом. Добавьте сущности **«Покупатель»** и **«Заказ»**.
2. У покупателя добавьте атрибуты **«ID покупателя»**, **«Имя»**; у заказа — **«ID заказа»**, **«ID покупателя»**, **«Дата»**. Пустая строка таблицы добавляет атрибут; двойной щелчок по строке открывает форму.
3. На физическом листе задайте SQL-имена `customer`, `orders`, колонкам `id`, `name`, `customer_id`, `created_at`. Для ID выберите одинаковый тип bigint, имени text, даты date. ID и обязательные поля сделайте non-null.
4. Выделите строку ID каждой таблицы и выполните **«Сделать PK»**. Для составного ключа выделите несколько строк Ctrl/Shift; проверьте порядок и предлагаемое снятие nullable.
5. Выберите заказ → **«Создать FK…»**. Дочерняя колонка customer_id должна ссылаться на первичный ключ покупателя. Просмотрите пары и правила до применения.
6. Для отношения задайте смысл **«Покупатель оформляет заказ»**: покупатель имеет 0…many заказов, заказ относится к 1…1 покупателю. Проверяйте подписи у конкретных концов, не по положению фигуры.
7. Добавьте второй лист, покажите существующие сущности. На концептуальном покажите атрибуты: владелец и связь атрибута добавляются вместе. Проверьте готовность и сохраните.

Итог: покупатель существует независимо от заказов, каждый заказ имеет одного покупателя; FK связывает конкретные колонки, а не только прямоугольники.

## Атрибуты, домены и ключи

Форма строки редактирует имя, SQL-имя, домен, тип, nullable. Enter или **«Применить атрибут»** принимает форму целиком, Escape отменяет. Перед сохранением/переключением завершите её. Расширенные параметры находятся справа.

| Возможность | Что задать |
| --- | --- |
| Домен | Повторно используемый тип: text, integer, decimal, boolean, date, datetime, uuid, binary, json |
| SQL-тип | Целые/числовые, строковые, boolean, date/time/timestamp/timestamptz, uuid, bytea, json/jsonb или custom |
| Размер | length для строк; precision/scale для чисел; customType для собственного типа |
| Значение | default, defaultSequence или identity none/always/byDefault по допустимому сочетанию |
| PK / UQ | Порядок частей; для UQ поведение NULL distinct/notDistinct |
| Порядок атрибутов | Меняет представление и порядок колонок, не устойчивый ID |

PK идентифицирует строку, UQ запрещает повтор значения/набора. Составной ключ — упорядоченный набор атрибутов одной сущности. Смена SQL-типа показывает затронутые FK; соседние колонки не меняются автоматически, несовместимое изменение отклоняется целиком.

## Отношения и внешние ключи

У бинарного отношения задаются min 0/1 и max 1/many с обеих сторон. weak у сущности и identifying у отношения включают соответствующее отображение. На концептуальном листе ключевые подчёркивания выводятся из PK; перенесённая часть ключа слабой сущности не изображается её собственным частичным ключом.

FK направлен **от дочерней таблицы к ключу родителя**. Мастер выбирает родительский PK/UQ и дочернюю колонку для каждой части; можно явно создать колонку по типу родителя. У составного FK порядок пар существенен. **«Изменить FK и пары…»** показывает изменения перед фиксацией; переподключение согласует затронутые листы.

Правила onDelete/onUpdate: restrict, noAction, cascade, setNull, setDefault; match: simple/full. Выбирайте по задаче. Например, setNull требует допуска NULL; cascade не следует включать только ради отсутствия предупреждения.

## Индексы, проверки и DDL

**«Добавить индекс…» / «Изменить состав индекса…»** задают имя, уникальность, btree, предикат и упорядоченные колонки с asc/desc и nulls default/first/last. Индекс не заменяет смысловой ключ.

Проверка CHECK хранит выражение и SQL-имя. После удаления используемого атрибута выражение требует ручного просмотра; подтвердите актуальность. До этого DDL блокируется. Бизнес-правило имеет уровень application/trigger/manual/unspecified: это описание места реализации, не готовый исполняемый код.

Последовательность на физическом уровне имеет SQL-имя/схему, start/min/max/increment/cycle. Ссылку на неё задайте у нужного атрибута. Схема/SQL-имя сущности позволяют отличить одинаковые человеческие подписи.

**«PostgreSQL DDL…»** создаёт предпросмотр принятой физической модели и позволяет сохранить текст. SQL не выполняется и БД не изменяется. Сначала исправьте блокирующие замечания; непроверенное выражение не следует выдавать за готовую миграцию.

## Оформление и ограничения

Овалы атрибутов, подписи, линии и ромб отношения можно размещать вручную; ромб остаётся на линии. Заметка и связь заметки поясняют модель. Общие цвета, закрепление, показ/скрытие отображений и PNG/PDF доступны независимо от DDL.

Профиль концептуального ER бинарный. N-арные отношения, составные/многозначные/производные атрибуты и специализация не реализованы. Проверяется структура модели, а не существующая база или безопасность SQL-выражения.
