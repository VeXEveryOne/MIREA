# UML — семь видов диаграмм

UML-проект хранит **общие элементы модели и независимые отображения на листах**. Реализованы варианты использования, классы, последовательность, коммуникация, компоненты, деятельность и развёртывание. Основные действия — в [общем руководстве](USER_GUIDE.md).

## Выбрать вид и работать с моделью

| Вопрос | Вид листа |
| --- | --- |
| Что пользователь хочет получить от системы? | Use case — варианты использования |
| Какие типы объектов, свойства и отношения нужны? | Class — классы |
| В каком порядке участники обмениваются сообщениями? | Sequence — последовательность |
| Как сообщения идут по связям участников? | Communication — коммуникация |
| Из каких компонентов и интерфейсов состоит система? | Component — компоненты |
| Как выполняется деятельность и передаются объекты? | Activity — деятельность |
| Где размещены артефакты и как связаны узлы? | Deployment — развёртывание |

Создайте нужный шаблон. **«＋ Лист модели»** добавляет другой вид в тот же документ; переключатель «Лист UML» открывает лист. Последовательность и коммуникация могут выбрать **одно существующее Interaction**. Смысл сообщения общий, геометрия разных листов независима.

Палитра показывает только допустимые типы активного вида. Фигура создаётся кнопкой; отношения доступны в группе «Связи» и списке **«Вид связи»** для протягивания между точками. «Свойства и события» содержит декларации без самостоятельной фигуры. В инспекторе владельца раздел **«Вложенные элементы»** добавляет его атрибуты, параметры, операнды и другие части.

Объект можно показать на нескольких листах без копирования. Delete убирает отображение, **«Удалить из модели…»** показывает каскад зависимостей. F2 меняет название, **«Переименовать ID…»** — ID и ссылки с предпросмотром. Наложение фигур не устанавливает семантическую принадлежность.

## Варианты использования

### Пример: оформить заказ

1. Создайте лист вариантов использования. Добавьте system **«Сервис заказов»**, actor **«Покупатель»**, usecase **«Оформить заказ»**, **«Проверить данные»**, **«Применить промокод»**.
2. Для вариантов укажите принадлежность системе через subject; расположите их отображения внутри рамки системы.
3. Participation соедините покупателя с «Оформить заказ».
4. Include направьте **от «Оформить заказ» к «Проверить данные»**: проверка включается в основной сценарий.
5. Extend направьте **от «Применить промокод» к «Оформить заказ»**, condition **«Промокод указан»**.
6. У «Оформить заказ» добавьте extensionPoint **«Расчёт суммы»** с location. У extend добавьте extension, выбрав эту точку расширяемого варианта.
7. У основного варианта запишите precondition **«Корзина не пуста»**, postcondition **«Заказ зарегистрирован»**, текст scenario. Проверьте готовность.

Include и extend различаются смыслом и направлением. Actor — внешняя роль, а не обязательно конкретный человек. Для обобщения actor/usecase используйте generalization от специализированного к общему.

### Все возможности вида

System задаёт предметную границу; subject — отношение варианта к системе. Actor/usecase могут иметь abstract. Participation задаёт участие. Usecase хранит предусловие, постусловие, описание сценария и ссылку на Interaction. При наличии последовательности этого Interaction **«Открыть сценарий»** переходит к ней. Extension имеет порядок точек применения, condition описывает условие. Примечание/ограничение поясняет элементы, но не исполняет сценарий.

## Классы

### Пример: покупатель и заказ

1. Создайте лист классов. Добавьте class **«Покупатель»**, **«Заказ»**, datatype **«Строка»** (primitive), **«Число»**. Они нужны как реальные classifier-ссылки, а не текст в имени атрибута.
2. У покупателя в «Вложенные элементы» добавьте attribute **«Имя»**, classifier «Строка», lower 1, upper 1. У заказа — **«Сумма»**, classifier «Число».
3. Добавьте operation **«Подтвердить»** у заказа. При необходимости добавьте параметр direction return с classifier результата.
4. Создайте association между классами. Проверьте два end: у конца покупателя кратность 1…1, у конца заказа 0…*, навигацию выберите по задаче.
5. Добавьте interface **«Хранилище заказов»** и class **«Сервис заказов»**. Realization направьте от сервиса к интерфейсу.
6. Настройте секции класса и расположение, проверьте готовность.

Association — объект отношения с концами, не единственная стрелка с двумя произвольными текстами. Кратность у конца описывает экземпляры класса этого конца.

### Классификаторы и части

| Возможность | Поля/действия |
| --- | --- |
| class | visibility public/private/protected/package, abstract, static, роль boundary/control/entity |
| interface | visibility, операции |
| datatype | primitive, visibility |
| enumeration / literal | Перечисление и упорядоченные значения |
| attribute | owner, classifier, lower/upper, visibility, abstract/static/readonly/derived/ordered/unique, default, order |
| operation | owner, visibility, abstract/static/query, order |
| parameter | owner-операция, classifier, lower/upper, direction in/out/inout/return, default, order |
| signal / signalAttribute | Сигнал и типизированные поля |
| associationClass | Отношение с собственными свойствами класса |

Верхняя кратность допускает `*`. Default хранится как текст. Скрытие секции name/attributes/operations/all меняет отображение, не удаляет части.

### Отношения

End задаёт classifier, кратность, navigation unspecified/navigable/nonNavigable, aggregation none/shared/composite, ownedBy, visibility, ordered/unique и order. Qualifier добавляет типизированное уточнение конца с кратностью/порядком. У association есть derived.

Generalization идёт от специализированного классификатора к общему, dependency — от зависимого к поставщику, realization — от реализации к контракту. Не заменяйте их одинаковой линией. Проверка владельцев/кратностей не является проверкой исполнимости классов.

## Последовательность

### Пример: сохранить заказ

1. Создайте Sequence: лист получает Interaction. Добавьте линии жизни **«Покупатель»**, **«Сервис»**, **«Хранилище»**. При наличии классов укажите classifier; selector различает выбранный экземпляр.
2. Создайте message **«Оформить заказ»**: выберите покупателя как отправителя, сервис как получателя, область новых событий — Interaction, sort synchCall. События отправки/получения создаются вместе.
3. Добавьте synchCall **«Сохранить заказ»** от сервиса к хранилищу.
4. Добавьте reply **«Заказ сохранён»** обратно, выбрав replyTo исходного вызова сохранения.
5. Добавьте reply **«Подтверждение»** сервис → покупатель с replyTo вызова оформления.
6. У сервиса добавьте execution: lifeline сервис, start событие получения оформления, finish событие отправки подтверждения.
7. Используйте **«↑ Раньше / ↓ Позже»** для порядка в одной области; проверьте причинность и готовность.

Вертикальная позиция следует событиям, а не свободному перетаскиванию стрелки. Изменение подписи не меняет порядок.

### События, сообщения и активации

Occurrence принадлежит Interaction/operand, имеет order и lifeline; destruction обозначает уничтожение. Message ссылается на send/receive. Для найденного/потерянного сообщения задайте один существующий конец вместо пары участников.

Sort: synchCall, asynchCall, asynchSignal, reply, createMessage, deleteMessage. Signature связывает операцию/сигнал, replyTo — исходный вызов. Argument хранит parameter, value/classifier/target и order. Execution задаёт start/finish и тип behavior/action; его границы должны согласовываться с событиями линии.

Кнопки **«Событие отправки» / «Событие получения»** открывают нужный occurrence. Перестановка сообщения меняет его события внутри одной области и проверяет весь граф. Для переноса через границы фрагмента меняйте владельцев явно.

### Фрагменты, ref и ограничения

Fragment имеет order, operator и coverage линий жизни. Создайте operand и задайте guard, order, min/max повторений, затем поместите события в этот operand.

| Оператор | Назначение в модели |
| --- | --- |
| alt / opt | Альтернативы / необязательная ветвь |
| loop | Повторение с границами |
| par | Параллельные ветви с частичным порядком |
| seq / strict | Слабое / строгое упорядочивание |
| break / critical | Прерывающая ветвь / критическая область |
| neg / assert | Недопустимое / утверждаемое взаимодействие |
| ignore / consider | Игнорируемые / рассматриваемые сигнатуры через filter |

Пример alt: после проверки два operand с guard «Данные корректны» и «Иначе», сообщения каждой ветви принадлежат её operand. Рисование рамки вокруг прежних сообщений не переносит их автоматически. В par более высокая строка другой ветви не создаёт последовательность.

InteractionUse **ref** ссылается на Interaction через refersTo, хранит result, аргументы и actual gates. У вызываемого Interaction находятся formal gates; match согласует точки. Gate также может быть inner/outer у рамки. **«Перейти к ref»** открывает последовательность вызываемого взаимодействия.

Ordering явно связывает события. Invariant фиксирует условие на линии жизни. Constraint имеет type constraint/time/duration, target, from/to, expression/min/max. Условия, временные выражения и фильтры сохраняются, но не вычисляются.

## Коммуникация

### Пример: тот же обмен по каналам

1. Нажмите «＋ Лист модели», выберите communication и **существующее Interaction** из примера Sequence.
2. Покажите покупателя, сервис, хранилище через «Показать существующий элемент».
3. Создайте connector покупатель ↔ сервис и сервис ↔ хранилище, owner — тот же Interaction.
4. У исходных сообщений выберите соответствующий connector и покажите их на листе. Задайте sequence **1**, **1.1** для вложенного вызова; call связывает сообщение с внешним вызовом.
5. Расставьте участников свободно; проверьте направления сообщений и откройте Sequence для сравнения.

Сообщения общие с последовательностью. Канал — отдельный объект; несколько сообщений используют один connector.

### Нумерация, сценарии и геометрия

Sequence задаёт номер, call — внешний вызов для вложенной нумерации, thread — параллельный поток, guard/iteration/parallel — обозначение условия и повторения. Они не исполняются. Sort меняет линию/наконечник, направление определяется send/receive.

Канал идёт между границами участников, при препятствии обходит его. Стрелки сообщений располагаются у канала, встречные направления — по разные стороны. У сообщения **«Открыть канал»** ведёт к маршруту; перемещение текста меняет только подпись. **«Автоположение подписи»** возвращает автоматическое размещение. Без отображения канала сообщение предлагает его добавить.

Для сложного Interaction создайте scenario, choice для выбранных operand, step для исходных сообщений и repeat для повторений loop. Choice хранит выбранную ветвь/число повторений; step.iteration и вложенные repeat уточняют повторения. **«Показать шаг на листе»** создаёт отдельное отображение повторного сообщения.

После изменения исходного Interaction проверьте ветви/шаги и нажмите **«Согласовать сценарий»**. Предупреждение не обновляет его автоматически. **«Исходная последовательность»** показывает рамки/невыбранные ветви; неразвёрнутые ref отмечаются явно.

## Компоненты

### Пример: интерфейс приёма заявок

1. Создайте Component. Добавьте component **«Веб-интерфейс»**, **«Сервис заявок»**, interface **«Приём заявки»**.
2. У сервиса добавьте interfaceUse с direction provided, у веб-интерфейса — required; выберите **один и тот же interface**.
3. Покажите интерфейс как классификатор с операциями либо компактно: шарик provided, розетка required. Это вид одного объекта.
4. Для составной системы создайте компонент **«Система заявок»**, part с classifier этих компонентов и порты у их классификаторов.
5. Создайте componentConnector kind assembly у системы; в мастере выберите части и их порты. Проверьте два componentEnd и совместимость направлений.
6. Для внешнего порта системы и внутренней части используйте delegation. Сохраните после проверки.

Для простого рисунка provided/required достаточно interfaceUse. Для структурного соединителя нужны реальные части/порты и общий владелец, а не только близкие шарик и розетка.

### Все возможности вида

Component имеет abstract. Part задаёт owner, classifier и lower/upper. Port принадлежит компоненту, classifier — один interface, conjugated обращает направление. InterfaceUse, usage, realization и dependency представляют контракты/зависимости; одинаковые отношения интерфейса отображаются без дублей. ComponentRealization связывает компонент с существующим классом — это локальная упрощённая запись.

ComponentConnector бывает assembly/delegation, имеет owner и два упорядоченных componentEnd с part/port. Несовместимая смена типа порта блокируется с указанием затронутых концов. Перенос part к другому owner — явная команда с согласованием отображений.

Порт крепится к границе родительского отображения: side left/right/top/bottom и offset 0…1 сохраняются при resize. Без родительского view сначала задайте его в расположении. Пример: `examples/component-ports.omni`.

## Деятельность

### Пример: проверить и обработать заявку

1. Создайте Activity. Добавьте initial, action **«Проверить заявку»**, decision **«Корректна?»**, action **«Зарегистрировать»**, action **«Сообщить об ошибке»**, merge, activityFinal.
2. ControlFlow соедините начало → проверка → decision. Ветви к действиям имеют guard **«Да»** и **«Иначе»**; затем обе идут в merge → final.
3. Добавьте partition **«Оператор»**, **«Сервис»**. Назначьте ответственность действиям через поле, либо включите Drop и просмотрите создаваемый partitionMember.
4. Для передачи объекта добавьте objectNode **«Заявка»**, inputPin/outputPin нужного действия с classifier и ObjectFlow.
5. Проверьте принадлежность Activity, охват дорожек и типы потока.

Decision выбирает ветвь, merge объединяет альтернативы. Fork разделяет параллельность, join синхронизирует; merge и join не взаимозаменяемы. ActivityFinal завершает деятельность, FlowFinal — отдельный поток.

### Все возможности вида

Activity хранит precondition/postcondition. Action: opaque с body или callBehavior со ссылкой behavior; **«Открыть Activity»** переходит к вызываемой деятельности при наличии листа. Decision имеет decisionInput, join — joinSpec; выражения описательные.

ObjectNode хранит classifier/state, pins принадлежат действию, имеют classifier и lower/upper. ObjectFlow проверяет известные типы и generalization; неоднозначный тип через управляющий узел предупреждается. ControlFlow задаёт управление; guard не исполняется.

Partition имеет represents/parent, partitionMember — явную ответственность отдельно от геометрии. **«Показать дорожки»** добавляет отсутствующие виды. Дорожки/fork/join меняют ориентацию, дорожки сворачиваются; это отображение. Смена Merge/Join или вида final проверяется предварительно. Pins крепятся к границе действия. Пример: `examples/activity-parallel-pins.omni`.

## Развёртывание

### Пример: сервис на двух узлах

1. Создайте Deployment. Добавьте device **«Сервер приложений»**, executionEnvironment **«Среда выполнения»** с owner-сервером, device **«Сервер БД»**.
2. Создайте artifact **«Сервис заявок»**, задайте fileName и version по известным сведениям.
3. Создайте deployment location=среда выполнения, artifact=сервис. Используйте команду размещения или явно включённый Drop с просмотром.
4. Если нужна реплика, добавьте другой узел и второе deployment **того же артефакта**. Копировать artifact не требуется.
5. Создайте communicationPath между узлами с protocol/port. Если в модели уже есть соответствующий component, добавьте manifestation artifact → component.
6. Проверьте отношения размещения, владельцев и каналы.

Расположение прямоугольника внутри сервера само по себе не создаёт deployment. Удаление одного размещения не удаляет общий артефакт.

### Все возможности вида

Node, device и executionEnvironment задают вложенность owner; device хранит hardware, среда — technology/version. Artifact хранит owner/fileName/version. Deployment имеет location/artifact; manifestation — from артефакта to компонента; communicationPath ненаправлен, port при наличии 1…65535.

DeploymentSetting хранит owner/key/value. Это локальное текстовое пояснение, не исполняемая спецификация развёртывания. Один artifact допускает несколько размещений и отображений. Пример: `examples/deployment-repeated-artifact.omni`.

## Общие для UML специальные свойства

Annotation поясняет target. Constraint хранит условие/время/длительность и ссылки. Description доступно у поддерживающих его элементов. Они не вычисляют UML/OCL.

Раздел расположения задаёт parent view, концы view-связи, отображаемый step и секции. Эти ссылки отличаются от owner и семантических концов. Можно менять размеры/координаты, закреплять фигуры, задавать точки маршрута строками `x y`, включать **«Автомаршрут»** и **«Автоположение подписи»**. У Sequence часть геометрии вычисляется из событий и не редактируется свободно.

Структурная раскладка сверху вниз/слева направо учитывает визуальных родителей и закрепление. Для последовательности сохраняется событийный порядок. Переподключение подходящих структурных отношений согласует затронутые отображения и показывает предварительный результат.

## Проверка и границы покрытия

Проверьте типы/владельцев, ссылки частей, кратности, направления include/extend и структурных отношений, события/причинность, порты, дорожки и размещения. Предупреждение сценария требует просмотра даже при сохранении файла.

Семь перечисленных видов редактируются; объектная диаграмма, составная структура, пакеты, профили, состояния, обзор взаимодействий и временная диаграмма остаются WIP. Реализован локальный профиль UML, а не вся метамодель стандарта. Модель не запускает код, не подтверждает совместимость серверов и не выполняет процесс.

Большой связанный пример — «BOM и публикация карточки» в окне создания; малые примеры компонентов/деятельности/развёртывания также доступны там. Файлы используют общий собственный язык и `.omni`.
