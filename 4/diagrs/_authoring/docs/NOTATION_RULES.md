# Справочник нотаций и решений OmniNotation

Версия 0.1 · 9 сентября 2026. База кода исследования: `5094376`. Это рабочая база требований, а не заявление о полном соответствии стандартам. Детальные незакрытые строки BPMN остаются в [docs/status/BPMN_CHECKLIST.md](status/BPMN_CHECKLIST.md).

## Как читать и дополнять

Каждое правило имеет стабильный ID. «Сейчас» описывает прочитанный код; «Цель» — требование к будущей реализации. Источники разделяются на пользовательские решения, стандарт, локальный профиль и архитектурную рекомендацию. Правило библиотеки само по себе не доказывает требование стандарта. Для нового правила записывать источник и раздел, область применимости, допустимый/недопустимый случай, уровень диагностики, точку реализации и способ проверки. Обновлять этот файл вместе с изменением логики.

## 1. Обязательные решения проекта

Источник: [AGENTS.md](../AGENTS.md), [docs/reference/LANGUAGE.md](reference/LANGUAGE.md).

| ID | Правило |
| --- | --- |
| CORE-01 | Единственный пользовательский язык общий: `тип id название ключ=значение`. Только у IDEF0 `arrow` допускается флаг `-h` между ID и названием для скрытия подписи. Один элемент на строку; необязательные параметры разделяются пробелами. Многословные/специальные значения и пустые подписи — в двойных кавычках. |
| CORE-02 | Заголовок первой строкой: `нотация id название`. Нет `\`, запятых, скобок и `;`. Старые формы читаются для миграции; новые примеры и генерация используют NS-TEXT-2. |
| CORE-03 | Типы и разрешённые параметры определяет адаптер нотации; общий парсер не означает готовую поддержку UML/IDEF0. |
| CORE-04 | XML запрещён в исходнике, контейнере, промежуточном представлении, импорте/экспорте и примерах приложения. Не использовать XML API зависимостей. |
| CORE-05 | Собственные версионируемые JSON-контейнеры содержат notation/model/source/draft/layout и сохраняются с единым расширением `.omni`. Внутренние форматы: DFD v3 с миграцией v1/v2, BPMN v3 и многоуровневый IDEF0 v4 с миграцией v1/v2/v3; UML зарезервирован. Старые нотационные расширения читаются только для совместимости. |
| CORE-06 | `source` соответствует принятой модели; `draft` может быть ошибочным. Ошибка применения не должна частично менять модель, расположение или скрытые свойства. |
| CORE-07 | ID стабилен при смене названия и перемещении. Переименование ID — отдельная операция со всеми ссылками, а не простая правка подписи. |
| CORE-08 | Сохранять комментарии и неизменённый текст. Расположение не кодировать в названиях или семантических параметрах. |
| CORE-09 | Сохранять свойства, которые текстовый редактор не показывает. Неподдерживаемое преобразование явно отклонять, а не молча упрощать модель. |
| CORE-10 | Текст, графика, свойства и расположение входят в согласованную историю. Undo после ошибочного черновика также должен быть возможен. |
| CORE-11 | Исполнение BPMN-процессов не входит в текущую задачу. Выражения сохраняются как данные. |
| CORE-12 | Тесты запускаются только после нового явного разрешения пользователя. Генерация грамматики, статическая проверка типов и сборка не доказывают поведение. |
| CORE-13 | Все нотации подключаются к одному хосту редактора через общий реестр адаптеров. Активный адаптер ограничивает палитру и автокомплит своими типами/параметрами; типы разных нотаций не смешиваются. |

## 3. DFD

Текущий источник правил — собственный профиль NS-DFD-GS-1, [валидатор](../src/validation/dfd.ts) и [адаптер](../src/language/parser.ts). Не выдавать его за полный универсальный стандарт DFD.

| ID | Правило | Сейчас / дальнейшая работа |
| --- | --- | --- |
| DFD-01 | Три вида блоков: process, entity, store; связь flow направленная и именованная | Есть |
| DFD-02 | ID блоков и потоков уникальны; оба конца потока существуют | Структурная ошибка блокирует текстовую модель |
| DFD-03 | Поток соединяет разные блоки; хотя бы один конец — process | `GS_CONNECTION`, error категории rule; модель при этом может быть принята |
| DFD-04 | Название блока/потока непустое | `GS_NAME`, error категории rule; не структурный запрет |
| DFD-05 | Изолированный блок и процесс без входа или выхода требуют внимания | Предупреждения качества; не запрет сохранения |
| DFD-06 | Данные и управление не смешивать: поток обозначает передаваемые данные | Методическое правило; имя процесса рекомендуется формулировать действием, потока — данными |
| DFD-07 | ID DFD ограничен латиницей, цифрами и `_`, первый символ не цифра | Общая грамматика допускает ещё `.`/`-`, но адаптер DFD их отклоняет |
| DFD-08 | Декомпозиция должна связывать процесс с дочерней диаграммой и именованными границами | Цель; сейчас один уровень |
| DFD-09 | Балансировку родитель/ребёнок сравнивать по направлению и идентичности данных; разбиение составного потока делать явным | Предлагаемый профиль декомпозиции; простого сравнения числа стрелок недостаточно |
| DFD-10 | Контекст, номера уровней и словарь данных должны быть отдельными свойствами | Цель; не кодировать иерархию только в ID |
| DFD-11 | Ручной ортогональный маршрут, положение подписи и крепления вдоль сторон блоков являются представлением потока, а не его семантическими параметрами | Есть в DFD v3 внутри `.omni` через `layout.routes`/`layout.labels`/`layout.attachments`; текст NS-TEXT-2 не меняется |

## 4. IDEF0

Уточнения пользователя 27.09 и 04.10.2026: `IDEF-LAY-20/21/22/23`, `IDEF-BRANCH-03` и `IDEF-TEXT-01` в [профиле IDEF0](IDEF0_RULES.md) задают лестницу уровней по ICOM-порядку: M1/C1 имеют базовый отступ 28, M2/C2 — ещё один тайл 20, далее по одному тайлу на номер. Ветви `branchOf` сохраняют общий маршрут, новые блоки получают пять клеток свободного места; возвратный Input к предшествующему блоку сначала проходит ниже блока-источника. Поддержаны растяжение/числовые размеры, расширение листа, размер шрифта и переносы. Рамка резервирует компактную полосу по связанным функциям, а не растёт пропорционально всем внешним стрелкам. Это правила редактора проекта, не дополнительные требования ISO. Ручные близкие крепления допускают локальное сближение; перпендикулярные пересечения не запрещены. Оформление хранится отдельно в IDEF0 v4, язык остаётся общим.

`IDEF-ICOM-UP-01`, 14.09.2026: новая внешняя стрелка дочернего листа автоматически создаёт подключённые интерфейсы до корня, с родительской стороной по роли I/C/O/M. Согласование исправляет также существующие несопоставленные потоки. Исключения — явные mapping/localOnly и неоднозначные роли независимых потоков; точный контракт в §3.1 IDEF0_RULES.md.

14.09–04.10.2026: локальное `IDEF-BRANCH-01` добавляет разветвление через ПКМ по стрелке и подключение к функции. `branchOf` задаёт дерево ветвей с общим выходным ICOM; `branchOffset` хранит положение на родительском маршруте. Все автоматические потомки одного внешнего корневого Control/Mechanism, включая вложенные ветви, используют одну точку fork и горизонталь своего C/M как общую шину; отводы идут вертикально напротив получателей без отдельных длинных обратных линий. Рамочный конец корня определяется независимо от source/target, ручной `branchOffset` сохраняет приоритет. С 27.09.2026 `IDEF-BRANCH-02` скрывает повторную подпись унаследованного имени на ветви, сохраняя имя в коде и интерфейсах декомпозиции. Join и полная Junction/Segment-модель не реализованы. Точный контракт — §3.1 [IDEF0_RULES.md](IDEF0_RULES.md).

`IDEF-EXPORT-01`, 27.09.2026: предлагаемое имя PNG для IDEF0 собирается из Node и Title текущего листа; снимок по-прежнему содержит весь лист от края до края согласно `IDEF-LAY-16`.

`IDEF-COLOR-01`, 27.09.2026: цвет стрелки показывает её роль на каждом уровне: Input — контрастный бордовый, Control — синий, Mechanism — коричневый, Output — тёмно-зелёный. Семантика определяется полем `role`, а не цветом.

`IDEF-LAY-14/19`, 27.09–04.10.2026: маршрут стрелки без ручных изгибов обходит функции ортогонально; длина имеет строгий приоритет, затем минимизируются повороты и только затем сближение независимых потоков. Перемещение участков и концов использует магнитную сетку полтайла 10 единиц, Alt отключает привязку; линия отображается тоньше без уменьшения области захвата. Маршруты листа рассчитываются один раз для неизменной версии модели/геометрии и переиспользуются при служебных render/measure/select-обновлениях. Preview перемещения наследует неизменённые маршруты и инвалидирует только редактируемую стрелку с её ветвями; перенос подписи не вызывает трассировку. Сохранённый маршрут сохраняется, если не проходит через функцию; при пересечении он пересчитывается для отображения. Точное ограничение — в [IDEF0_RULES.md](IDEF0_RULES.md).

`IDEF-LAY-20`, 27.09–04.10.2026: автоматические стрелки Control от верхней рамки и Mechanism от нижней рамки получают уровни по ICOM-порядку: C1/M1 — 28 единиц, C2/M2 — 48, C3/M3 — 68 и далее с шагом один тайл (20). Ветви сохраняют общий ствол и не занимают отдельный уровень. Рамка сохраняет компактный резерв по связанным функциям; препятствие возвращает обычный обход. Ручные маршруты не перераспределяются.

`IDEF-LAY-21/22`, 27.09.2026: новые функции из кода получают минимум пять клеток (100 единиц) свободного пространства, лист расширяется по габаритам, а выделенную функцию можно растянуть за нижний правый угол. Размер сохраняется в `layout.sizes` IDEF0 v4 и учитывается всеми креплениями и миниатюрой; собственный текст не меняется. Общий участок сохраняется только у потока с ветвями `branchOf` (`IDEF-BRANCH-03`), совпадения ролей для этого недостаточно.

Нормативная цель: [ISO/IEC/IEEE 31320-1:2012](https://www.iso.org/standard/60615.html), подтверждённый ISO в 2024 году; [IEEE](https://standards.ieee.org/ieee/31320-1/5545/) указывает принятие IEEE 1320.1-1998. Полный текст ISO ещё не сверён постатейно. Исторические правила [NIST FIPS 183](https://nvlpubs.nist.gov/nistpubs/Legacy/FIPS/fipspub183.pdf) сохраняют метку своего источника, а не переименовываются в ISO. Реализованы связанные листы A-0/A0/A1…, дерево, ICOM по ID, явные формы туннелей, IDEF0 v4 в `.omni`, история и восстановление. Полное покрытие стандарта не заявляется.

Полный реализационный профиль, модель данных, матрица соединений, правила ICOM/туннелей/Call Arrow, диагностические коды и критерии готовности зафиксированы в [IDEF0_RULES.md](IDEF0_RULES.md). Фактическое покрытие каждой области ведётся в [IDEF0_CHECKLIST.md](status/IDEF0_CHECKLIST.md). Перечень ниже остаётся кратким межнотационным указателем и не заменяет эти документы.

| ID | Правило нотации |
| --- | --- |
| IDEF-01 | Контекст A-0 содержит единственную функцию; A0 раскрывает её. У модели есть цель и точка зрения. |
| IDEF-02 | Обычная диаграмма декомпозиции содержит 3–6 функций; исключение контекстной диаграммы учитывать отдельно. |
| IDEF-03 | У функции Input входит слева, Control сверху, Output выходит справа, Mechanism входит снизу. Это порты блока, не ограничение размещения внешнего конца на рамке листа. |
| IDEF-04 | Вход преобразуется функцией, управление задаёт условия, механизм обеспечивает выполнение, выход является результатом. |
| IDEF-05 | Функция требует управления и выхода; вход и механизм могут отсутствовать. |
| IDEF-06 | Имена функций выражают действия; подписи стрелок — данные или объекты. |
| IDEF-07 | Номер функции, номер узла и ссылка на дочернюю диаграмму различаются. |
| IDEF-08 | Границы дочерней диаграммы согласуются с интерфейсом родительской функции через ICOM. |
| IDEF-09 | Туннелирование явно меняет отражение стрелки между уровнями; его нельзя выводить из отсутствующей связи. |
| IDEF-10 | Ветвление/слияние сохраняет смысл и подписи сегментов; пересечение линий само по себе не соединение. |
| IDEF-11 | Маршруты стрелок ортогональны: горизонтальные/вертикальные сегменты, без диагоналей. |
| IDEF-12 | ICOM указывает интерфейс родительской функции; роль стрелки у дочернего блока может отличаться. |
| IDEF-13 | Call Arrow — особый механизм ссылки на детализацию; у функции допускается не более одной такой стрелки. |

Текущий профиль `NS-IDEF0-31320-1-2012-1` использует `diagram`, `function`, `boundary`, `arrow`. Роль стрелки задаёт порт функции-получателя либо выход на границу; источник-функция всегда Output. Визуальные команды патчат общий текст, ошибки не меняют принятую модель, координаты хранятся отдельно. Действующая иерархия задаётся `diagram in=function`; порт идентифицируется парой arrow ID/end у родительской функции, mapping — `boundary parentArrow/parentEnd`. Выделенная модель ArrowSegment/Junction и ссылки на возобновление туннеля остаются планом. Сторона/роль порта — семантика, координаты/маршруты — layout. Точные действующие ограничения — §3.1 [IDEF0_RULES.md](IDEF0_RULES.md).

По запросу пользователя от 13.09.2026 лист имеет видимую рамку: внешние концы закреплены на выбранных сторонах, функции находятся внутри. Размер рамки и перемещения входят в историю и IDEF0-контейнер (`layout.frame`/`positions` со старой версии v2); v1 читается с миграцией геометрии. Это локальное правило `IDEF-LAY-09`, не утверждение о полной сверке ISO.

По следующему изображению пользователя добавлены редактируемые верхний/нижний штампы (`IDEF-LAY-10`). Ячейки меняют параметры/название `diagram` через общую историю и текст; Enter/blur/save принимают ввод, Escape отменяет. Context, Note, номер страницы и статус — документарные поля, не декомпозиция или сертификат соответствия.

По решению пользователя от 20.09.2026 снимок IDEF0 экспортирует ровно жёлтый лист (`IDEF-LAY-16`), включая рамку, штампы и подписи сторон, без внешнего отступа. Интерактивные порты, resize и элементы управления в изображение не входят. С 26.09.2026 Chromium отрисовывает выбранную область с масштабом до 4×; повышение качества не меняет границы снимка.

Уточнение пользователя 13.09.2026 — внешние входы, управление, механизмы и выходы самой диаграммы (`IDEF-LAY-11`). На рамке есть точки I/C/M/O; перетаскивание между рамкой и функцией создаёт настоящий boundary + arrow. При отпускании связи от блока на любом краю рамки конец создаётся там. `boundary direction=in|out` отделяет направление от `side`, ICOM остаётся связанным с родительским портом. Старые файлы читаются без переписывания исходника. Свобода стороны рамки — пользовательское решение, не новое правило о портах функции.

По решению пользователя от 26.09.2026 название потока показывается только на стрелке (`IDEF-LAY-17`), без повторной подписи и пустой плашки у края рамки. Boundary сохраняет имя в модели для синхронизации декомпозиции; у внешнего конца остаются компактные ICOM-код и маркер туннеля.

По решению пользователя от 26.09.2026 общие реквизиты верхнего штампа синхронизируются между всеми листами, пустые значения показываются без `...`, а CONTEXT строится как миниатюра непосредственного родителя с выделенным раскрываемым блоком (`IDEF-LAY-18`). Для A-0 выводится TOP. Это продуктовый контракт; форма контекста сверена с FIPS 183 C.4.1.5.

Старые data-крепления в первой/третьей четверти стороны центрируются при отображении и при следующем изменении маршрута |
| BPMN-14 | По продуктовому решению порты потока работают как широкие области захвата: обычный вход расположен слева, выход справа; Start показывает только выход, End — только вход, Boundary — только выход. У Activity левый боковой порт принимает только flow-вход, правый отдаёт только flow-выход, а верхний и нижний общие порты используются в обоих направлениях для Association с документами и хранилищами. Gateway имеет одиночный вход слева, одиночный выход справа и по одному общему двунаправленному порту по центру верхней и нижней стороны. Автоматический маршрут выбирает верхний порт для цели выше, нижний для цели ниже и правый выход для горизонтального хода; вход выбирается из левого, верхнего и нижнего портов. Обратная связь через правый выход перед возвратом сохраняет минимальный вынос вправо 60 единиц и отдельный вертикальный поворот, чтобы участки не накладывались и оставались редактируемыми. Области не видны до наведения непосредственно на них. Ручного режима типа связи нет: data-область или Text Annotation создаёт Association, боковые области между разными Participants — Message Flow, внутри одного процесса — Sequence Flow | Верхний и нижний порты Gateway и data-порты Activity/Data Object/Data Store принимают соединение в обоих направлениях и закрепляют стрелку по центру стороны. Сохранённые маршруты со старым креплением в четверти стороны центрируются при отображении и при следующем изменении маршрута. Выбранная сторона и вынос хранятся в waypoints. Автовыбор не отменяет семантическую проверку концов связи; недопустимая комбинация отклоняется целиком |
| BPMN-15 | По продуктовому решению длинное название Task сначала переносится внутри стандартной ширины. Если получается более четырёх строк, создаваемая из кода задача умеренно расширяется; высота растёт только под фактическое число строк | Для Task/Activity стандартная ширина 150, увеличенная — 190; существующий вручную увеличенный размер не уменьшается при переименовании |

Собственные решения: `process` + `type` задаёт вариант Activity; `event` + `position` — позицию; `definition` — определение; `flow` + `type` — вид связи. Реестр допустимых свойств пока находится в `src/ui/bpmn/applyText.ts`, а не в общей метамодели. Новые параметры должны появляться согласованно в декодировании полей, текстовой проекции, применении, свойствах, контейнере и диагностике. Поддержку составных событий, data associations, choreography/conversation вести отдельными строками чеклиста. Ни одна строка этого раздела не означает, что всё уже проверено.

## 8. Очерёдность дальнейшей работы

1. Согласовать блокирующие категории DFD/BPMN и описать реальные гарантии сохранения; диагностика `error` сейчас не везде блокирует.
2. Закрывать BPMN по существующей таблице: области/соединения → события → параметры/ссылки → сложные виды.
3. Спроектировать многодиаграммный контейнер и стабильные интерфейсы декомпозиции; затем DFD/IDEF0.
4. Спроектировать общий UML-реестр и views; начать с классов и use cases.
5. После отдельного разрешения проверять round-trip, откат, скрытые свойства, историю и сохранение, затем обновлять фактический статус поддержки.

REQ_DUPLICATE_CODE блокирует повтор кода; REQ_VERIFICATION_BASIS требует основание verified; REQ_STALE_VERIFICATION предупреждает о несоответствии подтверждённого текста. Оргструктура, WBS и FURPS+ — редакторские профили ТЗ ИМ, не требования OMG. История и контейнер общие с FUNCTION_TREE; область реализации/приёмки — [ведомость ИМ](plans/IM_NOTATIONS_IMPLEMENTATION.md).

## ИМ: уточнения локальных профилей, 28.09.2026

GANTT — собственный расчётный профиль: DAG, рабочие дни, четыре нижних ограничения и обратный проход резервов; не Microsoft Project и не ресурсное выравнивание. Milestone означает начало рабочего дня на границе интервала. Проектные даты/часы/ресурсы не объявляются фактическим внедрением. [Договорённости и команды](guides/IM_EDITORS.md), [постатейная приёмка](plans/IM_NOTATIONS_IMPLEMENTATION.md).

UML проверен по [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/PDF), главы 11, 15, 19: conjugated порт инвертирует направление; локальная componentRealization ссылается на существующий class; неизвестный/неоднозначный тип objectFlow даёт предупреждение. Модель с двумя концами componentConnector считается законченной; один конец — незавершённость, три — ошибка профиля. Рекурсивный classifier части и dependency cycle предупреждаются, owner cycle блокируется. Никакие выражения и параметры развёртывания не исполняются.
