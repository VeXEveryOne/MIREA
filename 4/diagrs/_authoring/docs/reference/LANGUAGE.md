# Общий язык OmniNotation

Синтаксис NS-TEXT-2, решение пользователя от 9 сентября 2026 года: один элемент — одна строка, тип, ID, название и необязательные параметры. У стрелки IDEF0 между ID и названием допускается флаг `-h` для скрытия подписи.

```text
тип id название ключ=значение другойКлюч="несколько слов"
```

Поля и параметры разделяются пробелами/табуляцией. Нет `\`, запятых, скобок и `;`. `=` оставлен для однозначного различения ключа и значения. Короткие значения можно писать без кавычек: `Клиент`, `task`, `PT5M`, `true`, `3`, `-2.5`. Пустое название — `""`. Многословные названия, выражения, URL и специальные символы — в двойных кавычках. В строках допустимы Unicode и JSON-экранирование (`\n`, `\"`, `\\`). Без кавычек поддерживаются латинские слова (начало буква/`_`), русские слова (начало русская буква) и целые/десятичные числа; в продолжении слова разрешены соответствующие буквы, цифры, `_`, `.` и `-`. Для остальных алфавитов использовать кавычки.

Допустимы пустые строки, `//` и `/* … */` комментарии. Перенос завершает объявление, кроме переноса внутри блочного комментария; перенос внутри строки записывается через `\n`. ID начинается с латинской буквы или `_`; далее латиница, цифры, `_`, `.` и `-`. DFD-профиль запрещает точки и дефисы. ID элементов/связей уникальны, ключ нельзя повторить в одном объявлении. Ссылки можно объявлять раньше элементов. Вложенность задаётся через `in`, а не отступами.

Заголовок первой строкой: `нотация id "название диаграммы"`. Нотации: `dfd`, `bpmn`, `idef0`, `uml`. Все нотации используют расширение `.omni`; IDEF0 поддерживает связанные листы и внутренний формат v4, UML — четыре вида листов и формат v1. Общая грамматика находится в `src/language/notation.langium`.

Автокомплит получает активную нотацию от открытого документа и использует общий реестр адаптеров. Базовый механизм заголовков, объявлений, параметров и ссылок общий; DFD, BPMN и IDEF0 добавляют собственные ключи, варианты и шаблоны. Список автоматически открывается при вводе, пробеле и `=`, вариант принимается Enter, Tab или щелчком. Изменение текста заголовка не переключает набор подсказок; другая нотация открывается как отдельный документ. В UML новые объявления предлагаются для активного вида листа; свойства и типизированные ссылки — для текущего объявления, включая элементы других листов.

## UML: четыре вида в одном документе

Геометрия UML не является синтаксисом языка: `layout.nodes` хранит прямоугольники views, `layout.edges` — ручные `label` и `bends`. Маршруты, переносы текста, размеры по содержимому и привязки сообщений вычисляет редактор. При принятом изменении порядка событий ручная подпись сохраняет смещение относительно сообщения; открытие файла ничего не перезаписывает. Дополнение 24.09.2026 не меняет NS-TEXT-2 и контейнер UML v1.

Профиль `NS-UML-2.5.1-1`. Полный реестр типов и параметров — `notationRegistry.UML.elements` (метаданные `src/notations/uml/profile.ts`). [Правила и источники](../UML_RULES.md), [границы покрытия](../status/UML_CHECKLIST.md).

UML-декларация не обязана быть узлом или бинарной связью. Все объявления находятся в `model.elements`; UML самостоятельно проверяет поля, владение и типы ссылок. `owner` — семантическое владение, `diagram` — лист отображения, `parent` у view — рамка представления. Общее поле `in` из других нотаций в UML не используется. Заголовок называет весь документ.

Полные предметные схемы хранятся в отдельной коллекции. Формы объявлений и допустимые параметры описаны в этом разделе.

Сообщение и два его отображения имеют разные ID; переименование service или его классификатора отражается на обоих листах. Аргументы без списка у типизированного вызова — неуточнённые значения (wildcards UML). При визуальном создании сообщения коммуникации канал создаётся/переиспользуется автоматически.

| Семейство | Объявления и основные параметры |
| --- | --- |
| Use case | `system`, `actor`, `usecase`; `subject owner=usecase system=system`; `participation/include/extend/generalization from=… to=…`; `extensionPoint owner=usecase location=…`; `extension owner=extend point=extensionPoint order=…` |
| Классификаторы | `class/interface/enumeration/datatype/associationClass`, `signal`; `role=boundary|control|entity`, `abstract`, `static`, `visibility=public|private|protected|package` — по типу |
| Члены | `attribute/operation/literal/signalAttribute owner=…`; `parameter owner=operation|interaction direction=in|out|inout|return classifier=… order=…`; typed-свойства имеют `lower`, `upper`, модификаторы по реестру |
| Ассоциации | `association`, отдельные `end owner=association classifier=… lower=0 upper="*" navigation=navigable aggregation=composite ownedBy=… order=…`; `qualifier owner=end classifier=… order=…`. Роль конца — его название |
| Взаимодействия | `interaction`, `lifeline owner=interaction classifier=… selector=…`; `occurrence owner=interaction|operand lifeline=… order=… destruction=true` |
| Сообщения | `message owner=interaction send=occurrence|gate receive=occurrence|gate sort=synchCall|asynchCall|asynchSignal|reply|createMessage|deleteMessage signature=… replyTo=… connector=…`; один конец можно опустить для found/lost |
| Аргументы / активации | `argument owner=message|interactionUse parameter=… value=… classifier=… target=… order=…`; `execution owner=interaction lifeline=… start=occurrence finish=occurrence` |
| Фрагменты | `fragment owner=interaction|operand operator=alt|opt|loop|par|seq|strict|break|critical|neg|assert|ignore|consider order=…`; `operand owner=fragment guard=… min=0 max="*" order=…`; `coverage owner=fragment|interactionUse lifeline=…`; `filter owner=fragment signature=…` |
| Ссылки / порядок | `interactionUse owner=interaction|operand refersTo=interaction order=… result=…`; `gate owner=… kind=formal|actual|inner|outer match=gate`; `ordering owner=interaction from=occurrence to=occurrence` |
| Условия | `invariant owner=interaction|operand lifeline=… condition=… order=…`; `constraint type=constraint|time|duration target=… from=occurrence to=occurrence expression=… min=… max=…`; `annotation target=…` |
| Коммуникация | `connector owner=interaction from=lifeline to=lifeline`; у message `call=message sequence=1 thread=a guard=… iteration=… parallel=true` |
| Сценарий | `scenario owner=interaction fingerprint=…`; `choice owner=scenario fragment=… operand=… iterations=1 iteration=0`; `step owner=scenario message=… order=0 iteration=1`; `repeat owner=step loop=fragment iteration=1` |
| Отображения | `diagram type=usecase|class|sequence|communication interaction=… scenario=…`; `view diagram=… element=… parent=view from=view to=view step=step compartments=all|name|attributes|operations` |

Таблица сокращает перечень параметров; допустимость задаётся конкретной строкой реестра. Роли анализа принадлежат class, `match` — gate, `replyTo` — ответу. `description` доступен у всех типов. Поля, концы, параметры, аргументы, события и повторы — самостоятельные строки со стабильными ID. Скрытие compartments не удаляет объявления.

`order` — локальный порядок внутри владельца (целое 0–1000000, при равенстве детерминированный порядок ID). Он не создаёт глобальной очереди: у par нет обязательного порядка между операндами. Изменение x линии жизни не меняет order. Метки `thread`, условия и псевдокод повторения не исполняются и не отменяют явно заданные причинные зависимости.

UML-контейнер `.omni` (также читается прежний `.nsuml`) содержит `formatVersion: 1`, `notation: "UML"`, `profile`, `model: {id,label,elements}`, `source`, `draft`, `layout: {nodes,edges}`. Ключ nodes — view ID, значение — `{x,y,width,height}`; у edges — необязательные `label: {x,y}` и `bends: [{x,y}]`. Геометрия последовательности частично производная: высота событий, активаций и фрагментов вычисляется из модели; ручные bends не меняют сообщения последовательности. Координат в NS-TEXT-2 нет.

Accepted source обязан соответствовать модели. Ошибочный draft может отличаться; он сохраняется без частичного применения. Неизвестные версии/профили, повреждённые refs и лишние/отсутствующие layout ID отклоняются до записи. Старые информационные WIP-вкладки не являются `.nsuml`-моделями.

## IDEF0: начальный профиль с целью ISO/IEC/IEEE 31320-1:2012

При применении кода новая внешняя стрелка дочернего листа автоматически получает отсутствующие родительские интерфейсы до корня. Принятый текст дополняется объявлениями стрелок/границ и parentArrow/parentEnd. Роли определяют стороны новых родительских соединений; явные сопоставления и localOnly сохраняются. Для старых несопоставленных стрелок используйте «Согласовать ICOM»; загрузка файла не дописывает их автоматически.

Разветвление (14.09–04.10.2026): необязательное `branchOf=ID_стрелки` у `arrow` связывает ветвь с исходной стрелкой. `from` у обеих стрелок совпадает, `to` и принимающая `role` могут отличаться. Например: `arrow extra Данные from=a to=c role=control branchOf=main` при существующей `arrow main Данные from=a to=b role=input`. Циклы запрещены. Выходной порт/его порядок/туннель общие: `fromOrder` и `tunnelFrom` задаются только у корневой стрелки. Положение ручной развилки хранится отдельно в `layout.arrows[id].branchOffset`, а не в тексте. Без сохранённой позиции всё внешнее семейство использует первый поворот корневой стрелки после рамочного отступа; внутреннее семейство выбирает участок непосредственного родителя ближе к получателю. Текстовые изменения ссылок и источников должны быть согласованными; удаление родителя из текста требует удаления или переназначения зависимых ветвей.

Только у стрелки IDEF0 необязательный флаг `-h` между ID и названием скрывает её подпись на текущем листе: `arrow controlArrow -h Правила from=rules to=A0 role=control`. Название остаётся в модели и коде, передаётся через ICOM на уровни декомпозиции и редактируется двойным щелчком по линии. Удалите `-h` или выберите «Показать название» в меню стрелки, чтобы вернуть подпись. У ветви с именем родителя повторная подпись может оставаться скрытой по правилу ветвления. Флаг у других типов и нотаций недопустим; форма `hideLabel=true` в тексте не поддерживается.

Полные предметные схемы хранятся в отдельной коллекции. Формы объявлений и допустимые параметры описаны в этом разделе.

Типы: `diagram`, `function`, `boundary`, `arrow`. В документе один корневой `diagram` и его дочерние листы. Корень использует `node=A-0`; дочерний лист указывает `in=ID_родительской_функции` и соответствующий номер `node=A0|A1|A11…`, а также `purpose` и `viewpoint`. Старый отдельный корень A0/A1… читается с предупреждением об отсутствии A-0. В заголовке модели параметры не поддерживаются. Функция использует `number=0` на A-0, цифры 1–6 на остальных листах; ID функции и номер блока не одно и то же. `in=sheet` у функции/границы задаёт её лист. Отсутствующий `in` означает корневой лист (совместимость старых текстов). У функции не более одного дочернего листа; циклы, несогласованные номера и стрелки между разными листами отклоняются.

У `boundary` обязательна сторона **рамки листа** `side=left|top|right|bottom`; `direction=in|out` задаёт направление независимо от стороны: `in` — из внешней среды в лист, `out` — из листа наружу. Для совместимости отсутствие `direction` означает `out` справа и `in` на остальных сторонах. Новые визуальные границы сохраняют направление явно; при визуальной смене стороны старой границы оно фиксируется без разворота стрелки. При текстовой смене стороны такого старого конца укажите `direction` явно. Например, `boundary result Результат side=top direction=out` — выход через верхний край листа. Необязательный `order=0` — порядок начальной раскладки (0–9999), не ICOM-код родителя. Это внешний конец стрелки, не блок: перетаскивание подписи двигает его вдоль стороны, смена стороны выполняется в свойствах. Функции остаются внутри рамки. Координаты и размер листа хранятся отдельно от текста; `Разложить` применяет авто-layout заново.

Верхний и нижний штампы редактируют саму строку `diagram`: `Title` — её название, `Node` — существующий `node`. Дополнительные необязательные параметры:

| Поле штампа | Параметр |
| --- | --- |
| USED AT / AUTHOR / DATE | `usedAt` / `author` / `date` |
| PROJECT / REV / NOTE | `project` / `revision` / `notes` |
| READER / DATE | `reader` / `readerDate` |
| CONTEXT / Number | вычисляется из иерархии / `pageNumber` |
| WORKING / DRAFT / RECOMMENDED / PUBLICATION | `status=working|draft|recommended|publication` |

Все поля, кроме `status`, — свободный текст до 2000 символов; даты не преобразуются и не заполняются автоматически. `Title` и `Node` сохраняют прежние ограничения названия и узла. USED AT, AUTHOR, DATE, PROJECT, REV, NOTE, статус и READER/DATE принадлежат модели: редактор показывает одно значение на всех листах и при правке любого листа атомарно обновляет все объявления `diagram`. Отсутствующий/пустой статус отображается как WORKING. CONTEXT вычисляется из иерархии: на дочернем листе это миниатюра непосредственного родителя с выделенным родительским блоком, на корневом A-0 — TOP. Старый параметр `context` читается и сохраняется для совместимости, но больше не управляет этой ячейкой. `notes` — текст, не графические маркеры; `pageNumber` не является номером узла. Эти поля не меняют состояние проверки стандарта. Например:

```text
diagram sheet "Проверка заказа" node=A0 author="Автор модели" date="13.09.2026" project="Обработка заказов" status=draft pageNumber=2
```

Щелчок по редактируемой ячейке открывает ввод; Enter/уход из поля принимают правку, Escape отменяет, Shift+Enter добавляет строку в многострочных полях. Пустая ячейка остаётся пустой, без `...`. CONTEXT является вычисляемой миниатюрой и не открывает текстовый ввод. Сохранение сначала фиксирует активное поле; неверный `node` или непринятый черновик блокируют фиксацию без потери модели/кода. Поля попадают в общую историю и остаются при других правках исходника. Штампы входят в модель контейнера v3; старый редактор, не знающий новые параметры, отклонит такую модель. Штампы рисуются вне `layout.frames[sheetId]`, не сдвигая координаты существующих функций и концов стрелок; внешние подписи размещаются внутрь рабочей области, чтобы не перекрывать штампы.

У `arrow` обязательны `from`, `to` и `role=input|control|output|mechanism`. Роль относится к **входному порту функции-получателя** либо к выходу на границу `direction=out`. Источник-функция всегда использует Output. Между функциями следует писать `role=input`, `control` или `mechanism`, не `output`. Входящая граница `direction=in` может находиться на любой стороне рамки, в том числе на A-0; сторона порта самой функции остаётся I/C/O/M. Сторона рамки не меняет роль или ICOM-код. Разветвление поддержано через branchOf; сквозные стрелки, join и Call ещё не реализованы. Геометрия маршрутов хранится в layout. Работающие декомпозиция, ICOM и две формы туннелей описаны ниже.

Прямой жест от порта функции до края листа создаёт `boundary` и `arrow` одной транзакцией. На самой рамке есть точки Input слева, Control сверху, Mechanism снизу, Output справа: соединение между такой точкой и функцией также создаёт внешний конец. Узел `diagram` не записывается как конец стрелки. На дочернем листе новое несопоставленное внешнее соединение даёт предупреждение ICOM, а не неявный туннель. Изменение направления подключённой границы без согласованной правки стрелок отклоняется. Формат контейнера остаётся v3; старое приложение без поддержки `direction` новые объявления не прочитает.

Код применяется кнопкой «Применить код». Неизвестные параметры, неверные номера/концы и неверная нотация блокируют кандидата; незавершённость (нет цели/точки зрения, Control/Output или нужного числа функций) даёт предупреждение. Черновик, визуальные правки и координаты входят в единую Undo/Redo-историю. Неприменённый черновик блокирует визуальные изменения и сохраняется вместе с последней принятой моделью. Сохранение/открытие проверяют согласованность модели, исходника и layout.

IDEF0 v4 в `.omni` содержит `profile=NS-IDEF0-31320-1-2012-1`, `model`, `source`, `draft`, `layout.frames` (ID листа → `x`, `y`, `width`, `height`) и `layout.positions` (глобальный ID элемента → координаты). Позиция функции — её левый верхний угол; позиция границы — точный конец стрелки на рамке, не угол подписи. Размер листа меняется в свойствах, участвует в Undo/Redo и сохраняется. `layout.arrows` — словарь по ID стрелок с необязательными `fromOffset`/`toOffset` (0–1 вдоль стороны функции), `bends` (внутренние точки маршрута), `label` (координаты подписи). Эти значения не являются параметрами NS-TEXT-2. Модель — собственный граф листа, функций, границ и стрелок; чужих форматов нет. Это частичный редактор, не полный ISO-валидатор. Происхождение правил и будущая модель — [IDEF0_RULES.md](../IDEF0_RULES.md), §3.1 имеет приоритет над целевым синтаксисом остальных разделов. Старый WIP-код требует строки `diagram`, исправления `number=A-0/A1` в `0/1` и ролей внутренних стрелок; автоматической миграции никогда не существовавших WIP-файлов нет.

Существующие `.nsidef0` v1 читаются с миграцией расположения: добавляется рамка вокруг функций, внешние концы проецируются на её стороны. ID, модель, исходник, отдельный черновик и абсолютные координаты функций сохраняются. Открытие не переписывает файл; следующее сохранение выпускает v4. Версия 2 мигрирует рамку в `frames` без сдвига элементов; v3 получает пустой `layout.arrows`. Прежнее приложение с поддержкой только v1/v2/v3 формат v4 не прочитает.

### Связанные листы, ICOM и туннели

Полные предметные схемы хранятся в отдельной коллекции. Формы объявлений и допустимые параметры описаны в этом разделе.

Это незавершённый пример: отсутствующие Control/Output у функций диагностируются. `diagram in=root` — декомпозиция функции root, не вложенный прямоугольник на одном полотне. `function/boundary in=child` — принадлежность листу. У стрелки нет `in`: лист определяется её концами, которые должны находиться на одном уровне. ID всех листов, функций, границ и стрелок уникальны в модели. Один корень, у функции максимум один child; циклы запрещены.

`parentArrow` и `parentEnd=from|to` у границы ссылаются на конкретный конец стрелки непосредственного родителя. Это устойчивое сопоставление, а ICOM-код вычисляемый. `fromOrder`/`toOrder` у стрелки — порядок соответствующего порта 0–9999; при равенстве используется порядок деклараций. Перестановка не меняет ID. Роль у дочерней функции может отличаться от роли родительского интерфейса. На A-0 parentArrow/parentEnd недопустимы.

`boundary tunnel=localOnly` явно означает отсутствие интерфейса у родителя и несовместим с parentArrow/parentEnd; на A-0 запрещён. `arrow tunnelFrom=true` либо `tunnelTo=true` у функционального конца явно исключает интерфейс из декомпозиции этой функции. false/отсутствие снимает этот туннель. Связь с ребёнком не удаляется автоматически: конфликтующее сопоставление надо изменить явно. Ссылки на возобновление туннеля через несколько уровней пока не поддержаны.

Визуальная смена номера блока пересчитывает номера descendant-листов. При текстовой правке номера и ссылки должны быть согласованы в одной транзакции. «Согласовать ICOM» дописывает недостающие границы, не внутренние связи. Правка Title дочернего штампа обновляет имя родительского блока; ручное текстовое расхождение имён диагностируется. Старый отдельный A0 можно обернуть в контекст соответствующей командой без замены его содержимого. Полный контракт — §3.1 [IDEF0_RULES.md](../IDEF0_RULES.md).

## DFD

Полные предметные схемы хранятся в отдельной коллекции. Формы объявлений и допустимые параметры описаны в этом разделе.

Типы: `process`, `entity`, `store`, `flow`. У `flow` обязательны `from` и `to`. Вложенность и дополнительные семантические параметры DFD пока не реализованы и отклоняются. Синтаксис старых DFD-файлов `dfd orders "…" { process receive "…"; }` остаётся читаемым; при открытии файл переводится на общий язык с сохранением комментариев. Ошибочный старый черновик сохраняется для исправления.

Корректная правка DFD-кода сразу обновляет модель. Визуальная правка меняет соответствующее объявление с помощью CST-диапазонов. Неизменённые объявления и внешние комментарии сохраняются; комментарии внутри изменяемого объявления переносятся перед ним. Координаты находятся отдельно в `layout` и не меняются при переименовании. DFD v3 в `.omni` хранит позиции блоков в `layout.positions`, внутренние точки ручных ортогональных маршрутов — в `layout.routes`, вручную перемещённые подписи — в `layout.labels`, а доли крепления вдоль правой/левой стороны блоков — в `layout.attachments` по ID потока. Без сохранённой геометрии используются середины сторон и автоматический маршрут. Широкие боковые зоны позволяют начинать и завершать поток не только на маленьком маркере; выбранная точка становится сохраняемым креплением. Выделенная стрелка показывает маркеры прямых участков и концов; drag перемещает участок либо крепление, Alt временно отключает магнит маршрута, Escape отменяет жест. Углы стрелок DFD, IDEF0 и BPMN визуально закруглены без изменения сохранённых точек. Старые v1/v2 открываются с миграцией; следующее сохранение выпускает v3.

Профиль NS-DFD-GS-1: процесс, внешняя сущность, хранилище, направленный именованный поток. Запрещены самосвязи и поток без процесса хотя бы на одном конце; требуются непустые подписи. Изоляция и отсутствие входа/выхода — рекомендации качества. Балансировка декомпозиции относится к следующему этапу.

## BPMN

Полные предметные схемы хранятся в отдельной коллекции. Формы объявлений и допустимые параметры описаны в этом разделе.

| Тип | Параметры варианта |
|---|---|
| `process` | `type`: `task` (по умолчанию), `user`, `service`, `manual`, `script`, `rule`, `send`, `receive`, `call`, `subprocess`, `transaction`, `adHoc` |
| `event` | `position`: `start` (по умолчанию), `end`, `catch`, `throw`, `boundary`; `definition`: например `timer`, `message`, `signal`, `error` |
| `gateway` | `type`: `exclusive` (по умолчанию), `parallel`, `inclusive`, `complex`, `eventBased` |
| `flow` | `from`, `to`; `type`: `sequence` (по умолчанию), `message`, `association`; `condition` для условия |
| `pool`, `lane` | Пул и дорожка; новые дорожки пока добавляются визуально |
| `data` | `type`: `object` (по умолчанию) или `store` |
| `annotation`, `group` | Аннотация или группа |

Дополнительные параметры:

- `documentation="…"` — описание элемента.
- `in=containerId` — контейнер элемента. Нельзя делать циклическую вложенность.
- Для BPMN строка `lane sales Продажи in=Participant_1` создаёт дорожку в уже существующем пуле, а `process approve Согласовать in=sales` назначает FlowNode этой дорожке. Назначение хранится в BPMN `flowNodeRef` и возвращается в код как `in=laneId`.
- `loop=standard`, `loop=parallel`, `loop=sequential`, `loop=none` — повторение действия; `cardinality=3` — число экземпляров или выражение.
- `definition=timer timeDuration=PT5M` — таймер. Вместо `timeDuration` допускается ровно одно из `timeDate` или `timeCycle`.
- `interrupting=false` — непрерывающий вариант Start/Boundary в допустимой области. Для Compensation Start атрибут не определяет поведение; вне Event Sub-Process у Start игнорируется стандартом и выдаёт предупреждение.
- `default=Flow_2` — исходящий поток по умолчанию у действия либо Exclusive/Inclusive/Complex Gateway.
- `compensation=true` — маркер компенсации действия.
- `eventName="…"` — имя определения Link.

None — отсутствие `definition`, а не отдельный тип. `definition=compensation` преобразуется в `CompensateEventDefinition`; старое `definition=compensate` тоже читается. Multiple — несколько определений, не `definition=multiple`; их редактирование собственным кодом ещё не реализовано.

Наличие параметра не разрешает все комбинации. [Правила BPMN и план](../BPMN_2_RULES.md) фиксируют реализованные проверки и пробелы. Ошибки семантики в `rules.ts` блокируют применение/открытие/сохранение кандидата; предупреждения о незавершённом построении не блокируют. Неизвестные параметры и преобразования вне поддержанного подмножества отклоняются. ID уже открытого корня нельзя менять из кода; название менять можно.

Общий код BPMN применяется кнопкой **«Применить код»**. Изменения сначала выполняются на отдельной объектной модели; только успешный результат заменяет рабочий документ. Визуальные правки обновляют код автоматически. Сложные свойства, ещё не вынесенные в язык, остаются в собственной семантической модели. Преобразование, которое потеряет несовместимые скрытые свойства, отклоняется. Поддержанные изменения входят в общую историю.

Граничное событие первоначально прикрепляется к действию на схеме. Первый пул создаётся визуально, поскольку эта операция меняет корень Process на Collaboration; после этого дорожки можно создавать и назначать из кода. Сложные скрытые подпроцессы, вложенные Lane Set, хореография и conversation-диаграммы не поддерживаются.

## Документы и восстановление

- `.omni`, DFD версии 3: `model`, `source`, `draft`, `layout`, `settings`; версии 1/2 читаются с миграцией геометрии.
- `.omni`, IDEF0 версии 4: многоуровневая модель, `profile`, `model`, `source`, `draft`, `layout.frames`, `layout.positions`, `layout.arrows`, необязательные `layout.sizes` (размеры функций) и `layout.textStyles` (шрифт, автоперенос, ширина подписи стрелки); версии 1/2/3 читаются с миграцией без записи на диск. Оформление не является параметром языка, явные переводы строк имени используют обычное строковое экранирование NS-TEXT-2.
- `.omni`, BPMN версии 3: `model` с семантическими объектами и явными ссылками, отдельный `layout` с объектами расположения, `source` и `draft`. Это собственный JSON-контейнер. Собственный редактор работает с графом через BpmnEdit; bpmn-moddle предоставляет только дескрипторы объектов. XML-парсеры и сериализаторы приложение не использует.
- `.omni`, UML версии 1: `profile`, общая `model`, `source`, `draft` и независимый `layout` по ID отображений. Листы и отображения — объявления общего текста. ID `__proto__` зарезервирован для совместимости JSON-декодирования. Старые UML WIP-снимки восстановимы как заглушки, неизвестные версии и повреждённые ссылки отклоняются без записи исходного файла.
- Старые расширения `.nsdfd`, `.nsidef0`, `.nsbpmn` и `.nsuml` распознаются при открытии существующих файлов. Новые документы и примеры сохраняются как `.omni`; нотация определяется полем `notation`, а не суффиксом имени. Экспериментальные BPMN-контейнеры версий 1–2 по-прежнему отклоняются без изменения исходного файла.
- Ошибочный `draft` не перезаписывает последнюю корректную модель. Пока черновик отличается от `source`, визуальные изменения блокируются. «Вернуть корректный код» возвращает текст; Undo позволяет отменить этот возврат.
- Сохранение атомарное. Восстановление использует общий кэш вкладок `workspace-v1.json` и `workspace-tabs-v1/*.json` в userData; содержимое документов различается полем `notation`. Историческое имя `recovery.nsdfd` не описывает текущий механизм вкладок.

## Совместимость синтаксиса

Парсер сначала читает NS-TEXT-2, затем прежний общий язык с разделителями; DFD дополнительно читает самый ранний диалект. Новые документы и подсказки используют NS-TEXT-2. При открытии/кодировании проекта корректный старый `source` упрощается с сохранением комментариев. Совпадающий с ним `draft` обновляется вместе с ним; отдельный черновик сохраняется побайтно. Модель, скрытые свойства и layout не пересоздаются. Чтение не переписывает исходный файл на диске.

Структурная версия DFD — v3 с чтением v1/v2; BPMN остаётся v3; IDEF0 перешёл на v4 с отдельной геометрией стрелок и миграцией v1/v2/v3. NS-TEXT-2 — имя синтаксиса, отдельного поля `sourceVersion` пока нет. Совместимость направленная: новая программа читает старые тексты, старая может не прочитать новые. Оба разработчика должны обновить приложение перед обменом файлами.

Исторические результаты прежних unit/E2E-проверок — в [TEST_REPORT.md](../status/TEST_REPORT.md); они не подтверждают новые UML-редакторы. Текущие разрешённые проверки и статическое прослеживание — в [UML_CHECKLIST.md](../status/UML_CHECKLIST.md).
