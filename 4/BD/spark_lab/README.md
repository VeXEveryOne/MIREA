# ТИАБД: практики №3 и №4

Здесь сохранены общие методички и исходный запуск `TIABD-Practice-2`.
Актуальные отчёты Албахтина И.В. пересобраны по новой отдельной VM;
[его ноутбуки, измерения, скриншоты и сборка](../АлбахтинИВ/README.md) лежат отдельно.

Обе работы фактически выполнены в Ubuntu 22.04.5 в VirtualBox: 2 vCPU,
4 ГБ RAM, Python 3.10.12, OpenJDK 17, Spark 3.5.7, `local[*]`.
Это локальная распределённая модель Spark, а не физический кластер.

## Артефакты

- Актуальные отчёты: [№3 DOCX](../Практическая%20работа%20№3.docx), [№3 PDF](../Практическая%20работа%20№3.pdf), [№4 DOCX](../Практическая%20работа%20№4.docx), [№4 PDF](../Практическая%20работа%20№4.pdf).
- [Practice_3.ipynb](Practice_3.ipynb): полностью выполненный notebook с Olist и самостоятельной обработкой продаж КОМУС.
- [Practice_4.ipynb](Practice_4.ipynb): полностью выполненный notebook, самостоятельный вариант B — `order_items` + `sellers`, агрегация по `seller_state`.
- `assignment/`: предоставленные методички, а не копии итоговых отчётов.
- `results/`: фактические JSON-результаты; для №4 также снимки REST API Spark UI и физические планы.
- `exports/`: обезличенные агрегаты CSV/Parquet и `_SUCCESS`; служебные CRC-файлы не входят в Git.
- `screenshots/pr3/`, `screenshots/pr4/`: реальные снимки framebuffer VirtualBox и страницы Spark UI. Их содержимое не рисовалось и не генерировалось.
- `source_manifest.json`: происхождение, количество строк и контрольные суммы источников.

## Источники и отличия от примера

Файл `ecommerce.sqlite` не был предоставлен. Для выполненного запуска он
восстановлен из одиннадцати CSV Olist, использованных во второй практике.
Две добавленные во второй практике записи перевода категорий исключены только
из реконструкции: справочник снова содержит 71 строку. Исходные CSV не менялись.
В этой версии 100 000 отзывов вместо 97 621 в примере методички; числа не
подгонялись. Все реальные количества сохранены в манифесте.

Для самостоятельной части №3 выбран архив «Транзакции КОМУС.zip»:
865 222 продажи и 21 163 товарных ключа справочника. Клиентские реквизиты,
адреса и номера машин исключаются на стадии подготовки. Сырые архивы и
транзакции остаются только локально в VM, в Git не включены. Предоставленные
`transactions.zip` и `northwind_small.sqlite` не нужны для выбранного набора:
КОМУС покрывает требования самостоятельной части.

86 431 продажи без себестоимости сохраняются в выручке, но имеют `margin=null`.
Маржа не равна чистой прибыли; её охват отражён отдельным `cost_known`.
Чтение Parquet сохранило имена и типы, но изменило nullable агрегатов — полное
равенство `StructType` не заявляется.

## Повторный запуск в Ubuntu

Рабочий каталог использованного стенда — `/home/student/spark-lab`.
Скопировать туда содержимое этого каталога, кроме отчётов и кэшей.

```bash
cd ~/spark-lab
bash setup_ubuntu.sh
```

Подготовить предоставленную SQLite и архив КОМУС (пути заменить на свои):

```bash
.venv/bin/python prepare_sources.py --database /path/ecommerce.sqlite --komus '/path/Транзакции КОМУС.zip'
```

Либо явно восстановить SQLite из CSV Olist, как в данном запуске:

```bash
.venv/bin/python prepare_sources.py --olist-csv /home/student/tiabd/data --komus /home/student/komus.zip
```

Затем выполнить оба ноутбука в новых ядрах:

```bash
.venv/bin/python execute_notebook.py Practice_3.ipynb
.venv/bin/python execute_notebook.py Practice_4.ipynb
```

`execute_notebook.py` сохраняет outputs и сообщает `RUN ALL SUCCESS` только
после выполнения всех ячеек. Обычный запуск не ждёт скриншотов.
Также можно открыть notebook через `.venv/bin/jupyter lab --ip=0.0.0.0`, выбрать
ядро этого окружения и выполнить Restart Kernel and Run All Cells.

`build_notebooks.py` заново создаёт исходные notebooks и **сбрасывает outputs**;
его не требуется запускать для просмотра готовой работы. После изменения
исходного кода выполнить оба notebooks заново. Новые измерения могут отличаться
от сохранённых: время зависит от прогрева и нагрузки.

Для ручного захвата Spark UI запустить исполнение с `TIABD_CAPTURE=1`.
`lab_helpers.py` оставляет контрольные паузы и пишет запросы в
`capture_requests/`: снять нужную вкладку живого UI `http://<IP-VM>:4040`, затем
создать соответствующий файл `.done`, названный в выводе notebook. Снимки должны
быть получены с реального экрана; старые кадры не выдавать за новый запуск.
`show_results.py` выводит сохранённые фактические результаты в консоли VM для
читаемых кадров. Профиль `skewed16` считает min/max/mean по непустым разделам;
профили четырёх выходных разделов в таблицах отчёта включают все четыре.

## Сборка отчётов

На Windows из этого каталога, используя Python с `python-docx` и Pillow:

```powershell
python build_reports.py
python verify_artifacts.py
powershell -File export_pdf.ps1
```

DOCX строятся из `results/pr3.json`, `results/pr4.json` и настоящих скриншотов.
Титульный макет берётся только из первой страницы ИСУРО; основная часть имеет
собственные настройки по общему справочнику. `export_pdf.ps1` требует Word
и использует отдельный невидимый экземпляр, не закрывая пользовательские окна.
После каждой пересборки необходимо визуально проверить **все** страницы PDF.
Промежуточный экспорт и PNG проверки хранить в корневой `.cache/`, не в Git.

Основная серия №4 имеет AQE=false, SQL shuffle partitions=8 и отключённый
автоматический broadcast. Число входных разделов от этих параметров не зависит
напрямую. Короткие замеры и результаты на двух vCPU не являются универсальными
рекомендациями о производительности кластеров.
