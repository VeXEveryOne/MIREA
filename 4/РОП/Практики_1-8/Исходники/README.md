# Сборка комплекта РОП

`config.py` и `runtime.mjs` определяют пути относительно расположения исходников. Общий модуль `tools/runtime.mjs` находит внешние библиотеки и исходники OmniNotation; путь к нему можно изменить переменной `OMNINOTATION_ROOT`. Копии `node_modules` внутри учебных материалов не нужны.
Для изолированной проверки сборки `ROP_ROOT` направляет результаты и входные материалы в отдельную копию комплекта.

Python-зависимости: `python-docx`, `pypdf`, Pillow; для визуальной проверки нужен пакет инструментов документов. Node использует `tsx` из OmniNotation, а также комплектные `sharp`, Playwright и `@oai/artifact-tool`. Экспорт PDF выполняется установленным Microsoft Word через COM.

Последовательность работы:

1. `schema.py` формирует модель БД и SQL; `drafts.py` — исходные SVG/JSON. `render_svg.mjs` получает PNG этих схем.
2. `rebuild_process_models.mts` обновляет четыре процессные модели в `../Модели/`; `fix_as_is_bpmn_layout.py` применяет раскладку BPMN AS IS. `validate_native.mts` проверяет IDEF0 и BPMN.
3. Для всех 38 рисунков использовать `../Модели/Экспорт_PNG.json` в пакетном экспорте OmniNotation. Четыре листа IDEF0 можно повторно получить через `capture.mjs` при запущенном локальном интерфейсе OmniNotation.
4. `content.py` собирает содержание; `baseline_tables.json` хранит исходные таблицы первой практики и FR/NFR. `terminology.py` содержит единые правила терминологии.
5. `build_report.py` создаёт канонические DOCX и Markdown. Титульный лист берётся только из первой страницы `4/ИСУРО/ИСУРО_1_АлбахтинИВ.docx`. `export_word.ps1` обновляет содержание и создаёт канонический PDF.
6. `render_with_word.py DOCX PDF ПАПКА [DPI]` растеризует PDF для визуальной проверки; папку проверки размещать в `.cache/rop/`.
7. `slides.mjs [первая_практика] [последняя_практика]` создаёт презентации. Практика 1 содержит 15 слайдов, практика 2 — 10, остальные — по 6.
8. `sync_final_outputs.py` обновляет реестр рисунков и хэши; `package_check.py` проверяет комплект; `final_audit.py` выполняет итоговую сверку. Повторные копии отчёта и моделей не создаются.

`validate_native.mts` открывает все 12 проектов через декодер OmniNotation; для IDEF0/BPMN дополнительно выполняет профильную проверку. `normalize_model_sources.mts имя.omni ...` восстанавливает принятый DSL из сохранённой структурированной модели, предварительно проверяя её и сохраняя геометрию. Использовать после контролируемого изменения модели, затем повторить экспорт при изменении отображаемых данных.

Пример проверки из этого каталога:

```powershell
python sync_final_outputs.py
python package_check.py
python final_audit.py
```

Для запуска TypeScript использовать `node <OMNINOTATION_ROOT>/node_modules/tsx/dist/cli.mjs validate_native.mts`. После изменения отчёта обязательны визуальная проверка страниц и обновление реестра. Результаты машинной проверки не заменяют просмотр вёрстки.
