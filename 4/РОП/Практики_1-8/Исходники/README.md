# Сборка комплекта РОП

`config.py` и `runtime.mjs` определяют пути относительно расположения исходников. Общий модуль `tools/runtime.mjs` находит внешние библиотеки и исходники OmniNotation; путь к нему можно изменить переменной `OMNINOTATION_ROOT`. Копии `node_modules` внутри учебных материалов не нужны.
Для изолированной проверки сборки `ROP_ROOT` направляет результаты и входные материалы в отдельную копию комплекта.

Python-зависимости: `python-docx`, `pypdf`, Pillow; для визуальной проверки нужен пакет инструментов документов. Node использует `tsx` из OmniNotation, а также комплектные `sharp`, Playwright и `@oai/artifact-tool`. Экспорт PDF выполняется установленным Microsoft Word через COM.

Последовательность работы:

1. `schema.py` формирует модель БД и SQL; `drafts.py` — исходные SVG/JSON. `render_svg.mjs` получает PNG этих схем.
2. `rebuild_process_models.mts` и `fix_as_is_bpmn_layout.py` восстанавливают первоначальные процессные модели. После них обязательно запускать `apply_review.mts`: он применяет замечания от 21.10.2026 к IDEF0, BPMN, ERD, портам компонентов, алгоритмам и примечаниям. `migrate_review.py` обновляет реестр до 30 рисунков, сохраняя стабильные идентификаторы экспорта. `validate_native.mts` проверяет все 12 проектов.
3. Для экспорта использовать `../Модели/Экспорт_PNG.json`. Печатные генераторы: `build_print_idef0.mts`, `build_print_bpmn.mts`, `build_print_data.mts`, `build_print_algorithms.mts`, `build_print_structure.mts`, `build_print_components.mts` и `build_print_sequences.mts`. Логическая модель в практиках 3 и 7 содержит все 29 сущностей, 185 атрибутов и 47 связей на одном рисунке. Имена атрибутов берутся из `logical_labels.json`; SQL-имена сохраняются отдельно. Длинные последовательности разделены на 11 частей с сохранением сообщений и условий. `fix_wireframe_terms.mts` согласует подписи экранов с текстом; `build_print_wireframes.mjs` экспортирует шесть экранов штатным скрытым CLI OmniNotation с актуальными номерами подписей и стабильными именами файлов.
4. `content.py` собирает содержание; `baseline_tables.json` хранит исходные таблицы первой практики и FR/NFR. `terminology.py` содержит единые правила терминологии.
5. `build_report.py` создаёт канонические DOCX и Markdown. Титульный лист берётся только из первой страницы `4/ИСУРО/ИСУРО_1_АлбахтинИВ.docx`. `export_word.ps1` обновляет содержание и создаёт канонический PDF.
6. `render_with_word.py DOCX PDF ПАПКА --dpi 110` растеризует PDF для визуальной проверки; папку проверки размещать в `.cache/rop/`.
7. `slides.mjs [первая_практика] [последняя_практика] [номера_через_запятую]` создаёт презентации. Практика 1 содержит 15 слайдов, практика 2 — 10, остальные — по 6. Последний аргумент необязателен и позволяет обновить только нужные презентации.
8. `sync_final_outputs.py` обновляет реестр рисунков и хэши; `package_check.py` проверяет комплект; `final_audit.py` выполняет итоговую сверку. Повторные копии отчёта и моделей не создаются.

`validate_native.mts` открывает все 12 проектов через декодер OmniNotation; для IDEF0/BPMN дополнительно выполняет профильную проверку. `normalize_model_sources.mts имя.omni ...` восстанавливает принятый DSL из сохранённой структурированной модели, предварительно проверяя её и сохраняя геометрию. Использовать после контролируемого изменения модели, затем повторить экспорт при изменении отображаемых данных.

Пример проверки из этого каталога:

```powershell
python sync_final_outputs.py
python package_check.py
python final_audit.py
```

Для запуска TypeScript использовать `node <OMNINOTATION_ROOT>/node_modules/tsx/dist/cli.mjs validate_native.mts`. После изменения отчёта обязательны визуальная проверка страниц и обновление реестра. Результаты машинной проверки не заменяют просмотр вёрстки.

`validate_review.mts` проверяет конкретные замечания: выходы IDEF0 только в следующий блок, слияния и пулы BPMN, русские атрибуты и связность ERD, порты UML, подписи алгоритмов и удаление примечаний ПР6/ПР8.

После проверки от 26.10.2026 генераторы используют `route_print.mts`: независимые связи получают отдельные маршруты, а поворот одной линии не может касаться другой линии, создавая ложный Т-образный стык. В BPMN точки входа и выхода шлюзов разделены. В ERD сохранены все 47 связей; для кратностей и подключений зарезервированы отдельные участки границ сущностей. В схеме массовой замены возвраты объединяются в явном соединителе «А». Развёртывание `schema.sql` показано вложением артефакта в среду PostgreSQL.

`validate_arrows.py` проверяет именно экспортированные SVG: совпадающие участки, встречные наложения, касания углов и ложные соединения. Для IDEF0 разрешены только связи с явным `branchOf`; общие ветви дерева функций сохраняют смысл иерархии. Отдельно сверяются концы каждого потока BPMN с границами его исходного и целевого элемента, включая вершины ромбов. Результат записывается в `ПРОВЕРКА_стрелок.json`.
