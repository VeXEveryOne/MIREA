## Что действительно требуется по методичкам

- ПР1: IDEF0 AS IS, BPMN AS IS и диаграмма сравнения аналогов. Число уровней декомпозиции не зафиксировано. В существующих моделях есть контекст и A0, общий BPMN и подпроцесс.
- ПР2: IDEF0 TO BE, BPMN TO BE, дерево функций, диаграмма компонентов; сценарии Use Cases в таблице. Отдельная UML Use Case Diagram **не указана как обязательная**. Третий вид BPMN с повторами добавлен для уточнения NFR-10.
- ПР3: логическая ERD и **изображение схемы кодирования**, а также таблицы сущностей и кодификаторов. В примере Губарева отдельный рисунок кодирования не выделен; здесь он добавлен по методичке.
- ПР4: каркасные экраны, Activity Diagram и подробные сценарии. Количество экранов не установлено; шесть выбраны по задачам варианта. Методичка называет Figma; по запросу пользователя подготовлены черновики для собственного редактора.
- ПР5: блок-схемы алгоритмов и таблица показателей с формулами. Три алгоритма выбраны под вариант: цена/масса, выбор предложения, массовая замена. Их количество не задано методичкой.
- ПР6: инфраструктурная схема и сравнение IDE/СУБД. Дополнительные уровневые схемы из примера не обязательны, их смысл раскрыт в компонентной архитектуре.
- ПР7: физическая модель БД, словарь всех атрибутов, Deployment Diagram. DDL добавлен как полезная заготовка, обязательная часть задания — модель и описание.
- ПР8: **ровно два ключевых интеграционных сценария с Sequence Diagram**, схема разграничения, таблица ролей, RBAC и меры ИБ. Собственную спецификацию API разрабатывать не требуется.

## Как использовать в OmniNotation

1. Открывать `.nsidef0` и `.nsbpmn` через «Открыть». Геометрия хранится в контейнере; TXT — копия принятого собственного исходного языка.
2. В IDEF0 переключать A-0/A0. В BPMN TO BE доступны общий процесс, подготовка и публикация.
3. SVG и `.draft.json` **не являются импортируемыми проектами OmniNotation**. SVG служит визуальным черновиком, JSON содержит координаты, элементы и связи. Для ERD полный состав атрибутов, составные ключи и межвидовые FK находятся в `База_данных/model.json` и `schema.sql`.
4. После реализации соответствующей нотации перенести модель и заменить рисунок с сохранением подписи. Номера рисунков и таблиц в Word заданы полями SEQ.
5. В текущем registry.ts UML имеет editable=false и adapter=null. ERD, wireframes, обычные блок-схемы и дерево функций не имеют отдельных адаптеров. Их статус нельзя считать реализованным только по наличию названия в UI.

## Следующие нотации для реализации

Приоритет для этого комплекта: ERD → базовые блок-схемы/дерево → UML Component → UML Activity → UML Deployment → UML Sequence → каркасы экранов.

Минимальные возможности: сущности с атрибутами, PK/FK и кардинальностью; функции и иерархия; блоки ввода/вывода, ветвления и возвраты; компоненты и зависимости; действия и управляющие потоки; узлы, среды и артефакты; линии жизни, синхронные/асинхронные сообщения, ответы, активации, alt/loop. Для всех — собственный язык, версии контейнера и сохранение геометрии. Это перечень потребностей проекта, не изменение программы.

## Проверки и ограничения

Модели TO BE созданы функциями `idef0DocumentFromSource` / `captureBpmn`, сохранены через `encodeProject`, проверены реализованными валидаторами и отрисованы текущим web-редактором OmniNotation. Диагностики ошибок и предупреждений пусты. Это проверка профиля редактора, не сертификация стандарта и не исполнение процесса.
Встроенного экспорта PNG нет: иллюстрации получены из редактора с оформлением для печати. На условных исходящих потоках XOR скрыты лишние мини-ромбы, которые текущий renderer рисует поверх корректной семантики. Сам репозиторий OmniNotation не изменялся.
Модель БД и SQL — проектная заготовка. SQL не запускался на сервере PostgreSQL; межтабличные бизнес-инварианты и RBAC описаны отдельно и не считаются реализованными. Производительность, доступность и восстановление не измерялись. Контракты PC4Games/ITPartner и актуальные endpoint Ozon предстоит согласовать при реализации.
