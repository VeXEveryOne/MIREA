## 3. Общая модель документов и расширение архитектуры

### 3.1. Идентификаторы и контейнер

**MODEL-01.** Для новых семейств добавить значения реестра `ERD`, `FLOWCHART`, `FUNCTION_TREE`, `SCHEME`, `WIREFRAME`, `CHART`; заголовки языка соответственно `erd`, `flowchart`, `functree`, `scheme`, `wireframe`, `chart`. Три новых UML-вида имеют прежний заголовок `uml` и `diagram type=component|activity|deployment`.

**MODEL-02.** Новые семейства получают `formatVersion=1` и собственный идентификатор профиля: `NS-ERD-1`, `NS-FLOWCHART-1`, `NS-FUNCTION-TREE-1`, `NS-SCHEME-1`, `NS-WIREFRAME-1`, `NS-CHART-1`. Расширенный UML — `formatVersion=2`, профиль `NS-UML-2.5.1-2`, с явной миграцией UML v1. Версию существующих DFD/IDEF0/BPMN ради этой задачи не менять.

**MODEL-03.** Минимальный контейнер: `notation`, `formatVersion`, `profile`, `model`, `source`, `draft`, `layout`. `model` содержит ID документа, название и типизированные декларации. Их текстовая сериализация общая, семантика принадлежит адаптеру. На диске допускается знакомый UML-подобный список `{id, kind, label, properties}`, но в коде требуется типизированный доступ к полям, а не произвольное разыменование строк.

**MODEL-04.** Различать три идентичности: элемент предметной модели, лист, отображение элемента на листе. ID всех деклараций уникальны в пределах документа и стабильны при переименовании/перемещении. Один элемент может иметь разные views на разных листах. На одном листе второе отображение разрешать только явной командой, а не создавать случайно при перетаскивании из проводника.

**MODEL-05.** Новые семейства используют служебные объявления:

| Декларация | Поля | Назначение |
| --- | --- | --- |
| `diagram` | `type` из профиля; специализированная ссылка на владельца/сценарий при необходимости | Лист |
| `view` | обязательные `diagram`, `element`; необязательные `parent`, `from`, `to` | Отображение узла или отношения |
| `note` | `text`, необязательный `owner` | Содержательная аннотация |
| `noteLink` | `from=note`, `to=элемент` | Привязка аннотации, не бизнес-отношение |

UML сохраняет существующий синтаксис `diagram/view`; новые параметры не должны менять значение прежних. `parent` у view — визуальная вложенность. `owner` у элемента — семантическое владение. Совпадение прямоугольников не создаёт владение.

**MODEL-06.** Атрибуты сущности, поля таблицы каркаса, сегменты кода и прочие части обычно рисуются внутри view владельца без самостоятельного view. Для выбора строки UI использует пару `(viewId, elementId)`, а не сохраняет выдуманную предметную сущность. Самостоятельный view строки нужен только там, где это явно предусмотрено профилем.

**MODEL-07.** Схема `layout` новых документов: геометрия узлов по view ID, геометрия рёбер по view ID, оформление и параметры печати по diagram ID. Хранить прямоугольник, порядок наложения, ручные изгибы, позиции подписей, привязки к сторонам/строкам/портам, признак закреплённого положения. Координаты новых views — координаты всего листа, не viewport и не относительные значения от parent; перемещение контейнера явно сдвигает прямоугольники потомков. Координаты конечные; размеры положительные; циклы визуальных родителей запрещены. При расширении UML v2 мигратор сохраняет видимые положения v1 без автораскладки; если существующий механизм требует преобразования системы координат, оно должно быть точным и не менять рисунок.

**MODEL-08.** Порядок атрибутов, детей дерева, сегментов кода, столбцов и строк каркаса задаётся явным `order`, а не положением строк исходника или координатой. При равенстве `order` отображать стабильно по ID и выдавать предупреждение; команда упорядочивания записывает последовательные значения одной транзакцией.

**MODEL-09.** Удаление view не удаляет модель. Команда «Удалить из модели» показывает список зависимых деклараций и листов. Каскад вычисляется по типизированным ссылкам; строковый поиск ID внутри выражений не применяется. Комментарии и текстовые описания не являются ссылками.

**MODEL-10.** Общие правила значений: ID по существующему NS-TEXT-2; bool только true/false; order — неотрицательное целое, по умолчанию 0; отсутствующий optional ref означает отсутствие связи, а не ссылку на пустой ID. Числа должны быть конечными. Label/description/text допускают пустоту, если конкретный профиль не требует непустое значение для готовности. Неизвестный ключ или enum в source — блокирующая диагностика с подсказкой; не игнорировать их. Неизвестное поле поддержанной версии JSON также не отбрасывать молча: явная ошибка совместимости либо предусмотренная версией область расширений.

**MODEL-11.** Если у критичного семантического значения в таблице не указан default, его отсутствие не подменяется произвольным выбором: незавершённость отмечается до заполнения. Первая альтернатива в enum не является автоматическим значением по умолчанию. UI-команда создания может явно подставить документированный шаблон (например, decision binary), и этот выбор должен попасть в source.

| `src/main/` | Совместимость `.omni`, восстановление, пакетный экспорт; нотационные правила сюда не переносить |
| `docs/`, `examples/` | Фактическое покрытие, язык, руководство, примеры и ручная приёмка |

В `NotationAdapter` могут потребоваться дополнительные capability-поля для листов, подключения портов, печати и специализированных команд. Добавлять их обратно совместимо с прежними адаптерами. Видимость UI выводить из capabilities, а не из разрастающейся цепочки проверок названия нотации в `App.tsx`.

## 4. Ручной редактор: общий контракт

### 4.1. Создание и выбор

**UI-01.** В диалоге создания для каждой готовой нотации есть пустой документ и предметный пример. UML-вид становится «готовым» только после выполнения всего контракта. В пустом документе уже есть корректный заголовок и первый лист; отсутствие предметных элементов допустимо.

**UI-02.** Перетаскивание фигуры из палитры создаёт элемент модели и его view одной операцией. Клик по палитре включает режим размещения; Escape отменяет его. Ввод названия не заменяет автоматически ID после создания. ID генерируется из типа и свободного номера.

**UI-03.** Перетаскивание существующего элемента из проводника создаёт только view. Если нужное отображение уже есть на листе, выделить его; дублирование отображения — отдельное действие. Выбор фигуры показывает её свойства, ID модели и листы, где она используется.

**UI-04.** Enter/потеря фокуса завершают обычное поле; Escape возвращает значение. Для многострочного описания — отдельное многострочное поле с явным завершением. Русские названия и переносы текста поддерживаются. Подпись отношения редактируется независимо от названий концов.

### 4.2. Соединение

**UI-05.** До соединения пользователь выбирает тип отношения. При протягивании подсвечиваются допустимые цели, включая строку атрибута, порт или границу контейнера. Недопустимый конец не создаёт связь; объяснение содержит конкретное правило и разрешённый тип цели.

**UI-06.** Для составных отношений открывается компактный мастер: FK — пары колонок; компонентный connector — части и порты; deployment — узел и артефакт. Превью не является сохранённой моделью. «Создать» фиксирует весь набор деклараций сразу, «Отмена» не оставляет полусвязей.

**UI-07.** Переподключение меняет семантическую ссылку и геометрию атомарно. Если меняется тип владельца/число полей или возникают зависимые свойства, показать конкретный предлагаемый результат. Простое перетаскивание изгиба меняет только layout.

**UI-08.** Самосвязь разрешается по профилю: ERD — да, цикл алгоритма — да при подходящих концах; дерево — нет; остальные случаи определяются соответствующей таблицей отношений. Общего запрета «источник равен получателю» не вводить.

### 4.3. Геометрия и вложенность

**UI-09.** Перемещение группы, resize, изменение маршрута и подписи имеют локальное превью и одну запись истории при завершении жеста. Escape отменяет весь жест. Размеры учитывают заголовок, строки, значки и поля; обрезанный текст недопустим без явного режима сокращения с раскрытием.

**UI-10.** Ортогональная трассировка обходит блоки и видимые подписи по возможности; пересечение линий само по себе не создаёт узел связи. Ручные bends сохраняются при переименовании и применении текста. Если путь после resize проходит через блок, подсветить конфликт и предложить «Перестроить маршрут», не переписывая ручную геометрию молча.

**UI-11.** «Разложить лист» и «Разложить выделенное» — явные команды с отменой. При обычном применении текста размещать только новые элементы, сохраняя старые позиции и закреплённые элементы. Алгоритмы раскладки специализированные: иерархия для дерева, слои для алгоритмов, строки и колонки для ERD, вложенные области для Deployment/Wireframe.

**UI-12.** При перемещении контейнера его визуальные потомки движутся вместе с ним; семантически связанные, но не вложенные views не перемещаются. При drop внутрь контейнера заранее показывать, будет ли изменён owner, membership, deployment либо только view parent. Случайное наложение не запускает такую команду.

**UI-13.** Поддержать выравнивание, равные интервалы, сетку, направляющие, fit, масштаб и панорамирование в рамках существующих жестов. Нельзя добавлять Ctrl/Cmd+A для выделения диаграммы: вне текстовых полей он поглощается по правилу проекта. Для выбора всех объектов использовать явную команду меню, если она нужна конкретному сценарию.

### 4.4. Буфер, удаление, поиск

**UI-14.** Копирование внутри документа различает «ещё одно отображение» и «дубликат модели». Дубликат получает новые ID собственных частей; наружные ссылки сохраняются, если допустимы. Копирование в другой документ той же нотации переносит необходимые зависимости с предварительным перечнем. В другой тип нотации вставка отклоняется, если нет отдельного именованного преобразования.

**UI-15.** Delete/Backspace удаляет выбранные views согласно платформенному контракту. Для подэлемента таблицы/формы действие «Удалить атрибут/поле» явно удаляет модельную часть и показывает затронутые связи. Удаление контейнера должно предлагать понятный выбор: убрать только отображение вместе с его вложенными views либо удалить модель с каскадом.

**UI-16.** Поиск охватывает ID, подпись, описание и имена атрибутов текущего документа. Результат показывает вид и лист; переход открывает нужный лист, выделяет view/строку и строку кода. Элемент без view открывается в проводнике с действием «Показать на текущем листе».

## 5. Кодовый редактор и двусторонняя синхронизация

### 5.1. Грамматика и примеры

**CODE-01.** Сохранить NS-TEXT-2. В заголовке — нотация, ID, название; далее `тип id название ключ=значение`. Имя обязательно синтаксически, пустое обозначается `""`. Значения с пробелами/специальными символами заключаются в двойные кавычки. Внутри строк применяются существующие JSON-escape. Комментарии — существующие `//` и `/* … */`.

**CODE-02.** Запятые, скобки, обратная косая черта и `;` не являются структурными разделителями деклараций. Их наличие внутри кавычек допустимо как данные выражения/описания. Множественные ссылки задаются отдельными объявлениями частей (`keyPart`, `fkPart`, `member`, `interfaceUse`), а не строкой `ids="a,b,c"`. Повтор ключа в одной строке — ошибка.

**CODE-03.** Ссылки допускают объявления вперёд. Сначала разобрать весь документ, затем разрешить ссылки и проверить типы. Смена заголовка с `erd` на `uml` не конвертирует открытый документ: выводится ошибка несоответствия нотации и предлагается создать другой документ отдельно.

**CODE-04.** Все примеры ниже — проект целевого языка. Их нельзя выдавать за код, который принимает версия приложения от 27.09.2026. После реализации примеры должны применяться штатным парсером. В примерах есть явные `view`: наличие семантического элемента без view не должно неожиданно создавать фигуру на каждом листе.

### 5.2. Поля, подсказки и действия Monaco

**CODE-05.** Профиль каждого поля содержит тип значения, обязательность, значение по умолчанию, русскую подпись, разрешённые enum, допустимые виды целей ссылки, кратность и область. UI и completion читают одни метаданные. Для новых параметров одновременно реализуются decode, encode, форма, проверка, renderer и сохранение.

**CODE-06.** Completion после типа предлагает уникальный ID и подпись; после пробела — ещё не заданные поля; после `=` — допустимые значения либо существующие элементы требуемого типа. Предложения ссылок содержат подпись, ID и владельца. Для полей колонки FK — только колонки выбранных таблиц; для port — порты выбранного типа части.

**CODE-07.** В документе с несколькими листами автодобавление предлагает типы активного листа. При редактировании уже существующей строки действуют поля её собственного типа независимо от открытого листа. Нельзя удалять/отклонять корректные Component-декларации потому, что пользователь сейчас смотрит Activity.

**CODE-08.** Переименование подписи меняет только label. «Переименовать ID» обновляет все типизированные ссылки и layout-ключи, если изменён ID view, одной транзакцией. Вручную отредактированный ID трактуется как удаление старого и создание нового, если ссылки не исправлены; приложение не угадывает переименование по похожему названию.

**CODE-09.** Поддержать переход к определению, поиск ссылок, подсветку диапазона диагностики, вставку шаблона элемента вместе с view, сортировку/форматирование только по явной команде. Форматирование сохраняет комментарии и не меняет смысл `order`.

### 5.3. Применение кода

**SYNC-01.** Последовательность: draft → синтаксическое дерево → полная кандидатная модель → проверка ссылок и правил → согласование сохранённой геометрии → один commit → перерисовка. При блокирующей ошибке меняется только draft и диагностика.

**SYNC-02.** Сохранить существующее автоприменение после 400 мс без ввода; «Применить код» выполняет его немедленно. При Undo/Redo, закрытии и переключении документа устаревший таймер не может заменить более новое состояние. Тяжёлый разбор должен проверять номер ревизии перед commit.

**SYNC-03.** Для новых нотаций вся пользовательская семантика должна иметь текстовую проекцию. Геометрия, оформление, положение панели и параметры масштаба не входят в source. Если расширение хранит скрытые свойства, они переносятся по стабильным ID; неизвестные данные нельзя молча отбросить при визуальной операции.

**SYNC-04.** Ручная команда сначала завершает ожидающее применение. При некорректном draft семантические визуальные изменения блокируются с выбором «Исправить код» / «Вернуть принятый код»; второе действие явно заменяет draft. Просмотр, поиск, pan/zoom и экспорт принятой модели доступны с указанием, что черновик не применён. Для единообразия layout-жесты также не фиксируются поверх ошибочного draft.

**SYNC-05.** Ручная правка патчит затронутые декларации по ID, сохраняет остальные строки и комментарии. При удалении декларации её собственные inline-комментарии входят в удаляемый диапазон; отдельно стоящие комментарии остаются. Система не перепечатывает весь документ после каждого drag.

**SYNC-06.** После изменения имени общей сущности все её views показывают новое имя; независимая геометрия листов остаётся. После изменения порядка строк пересчитываются крепления к строкам по element ID, а не по прежнему индексу.

## 6. Диагностика, незавершённость и история

**VAL-01.** Диагностика содержит стабильный `code`, `category`, `severity`, явный `blocksCommit`, сообщение на русском, ID элемента, при возможности view/diagram ID и диапазон исходника. Кнопка исправления — только отдельная проверяемая команда, а не скрытая мутация во время validate.

| Класс | Примеры | Применение/сохранение |
| --- | --- | --- |
| Структурная ошибка | Дубликат ID, отсутствующая указанная ссылка, неверный тип конца, цикл владельцев, NaN layout | Кандидат блокируется; draft сохраняется вместе с прежней моделью |
| Семантическое противоречие | Два PK у таблицы, owner другого типа, второй родитель функции, FK на неуникальный ключ | Блокируется |
| Незавершённость | Пустое имя, ещё нет PK, не задан тип, изолированный блок, решение без второй ветви | Предупреждение; документ разрешено продолжать строить |
| Качество представления | Пересечение, обрезанная подпись, слишком мелкая печать, одинаковые order | Предупреждение; экспорт сопровождается списком |
| Информация | Элемент модели нигде не показан, часть модели скрыта фильтром | Не блокирует |

**VAL-02.** Незавершённая фигура не должна требовать фиктивной ссылки. Например, новый атрибут допускает неизвестный тип с предупреждением, но `classifier=missing` является ошибкой. Соединение с обязательными концами создаётся целиком; полусвязь находится только в незавершённом жесте UI или ошибочном draft.

**VAL-03.** «Проверить готовность» усиливает выбранные предупреждения до нарушений готовности, но не запрещает сохранение чернового проекта. Для каждого профиля задать перечень таких предупреждений. Экспорт черновика разрешён после отображения статуса; значок «Готово» ставится только при чистой проверке готовности.

**HIST-01.** Одна пользовательская операция — один Undo: создание таблицы, FK с парами колонок, перенос поддерева, master-detail преобразование, раскладка, импорт и миграция в сеансе. Набор на клавиатуре группируется существующим механизмом истории; не создавать вторую историю Monaco, конфликтующую с документной.

**HIST-02.** Undo/Redo восстанавливают модель, source, draft, layout и зависимые декларации. После смены активного листа Undo не может применить жест к чужой геометрии. Выделение восстанавливается, насколько ID существуют; удалённый лист переключает на ближайший допустимый.

**HIST-03.** Save/Open проверяют согласованность принятого source и модели, существование layout-ключей и совместимость версии. Ошибочный draft не сравнивается как принятая модель. При повреждённом файле текущий документ не заменяется.

## 7. ERD: логическая и физическая модели

### 7.1. Назначение и профиль

**ERD-01.** Реализовать модель сущностей/атрибутов и ограничений с двумя представлениями: логическим (`diagram type=logical`) и физическим PostgreSQL (`type=physical`). В комплекте РОП это 29 сущностей, 185 атрибутов и по пять листов на каждый уровень, а не десять независимых БД.

**ERD-02.** На первом этапе одна сущность соответствует одной таблице, один атрибут — одной колонке. Логическое имя хранится в label, физическое — в `sqlName`, логический домен и физический тип раздельны. Это ограничение нашего профиля, не универсальное правило проектирования БД. Произвольное many-to-many сопоставление логической и физической моделей — расширение.

**ERD-03.** Логический лист показывает названия предметных сущностей, атрибуты, ключи, кратности и обязательность. Физический — имена таблиц/колонок, типы, длину/точность, NULL/NOT NULL, PK/FK/UQ и ограничения. Переключение вида не меняет модель; ручная геометрия двух листов независима.

### 7.2. Декларации и поля

Общие поля `id`, `label`, `description` доступны там, где имеют смысл. В таблицах ниже «обяз.» означает структурно обязательное поле; отсутствие остальных критичных данных диагностируется как незавершённость.

| Тип | Поля целевого языка | Назначение |
| --- | --- | --- |
| `entity` | `sqlName`, `schema=public` | Сущность/таблица |
| `domain` | `base=text\|integer\|decimal\|boolean\|date\|datetime\|uuid\|binary\|json`, `description` | Повторно используемый логический домен |
| `attribute` | `owner` обяз. entity; `domain`; `sqlName`; `sqlType`; `length`; `precision`; `scale`; `nullable=true`; `default`; `identity=none\|always\|byDefault`; `order` | Атрибут/колонка |
| `key` | `owner` обяз. entity; `kind=primary\|unique`; `sqlName`; `nulls=distinct\|notDistinct` для unique | Составной PK/UQ |
| `keyPart` | `owner` обяз. key; `attribute` обяз.; `order` | Колонка ключа |
| `relation` | `from`, `to` обяз. entity; `fromMin=0\|1`, `fromMax=1\|many`, `toMin=0\|1`, `toMax=1\|many`; `identifying=false` | Бинарная логическая связь |
| `foreignKey` | `owner` обяз. дочерняя entity; `targetKey` обяз. key; `relation`; `sqlName`; `onDelete`, `onUpdate=restrict\|noAction\|cascade\|setNull\|setDefault`; `match=simple\|full` | FK дочерней таблицы к PK/UQ родителя |
| `fkPart` | `owner` обяз. foreignKey; `attribute` обяз. дочерняя колонка; `target` обяз. колонка targetKey; `order` | Явная пара колонок |
| `check` | `owner` обяз. entity; `expression`; `sqlName` | Невычисляемое выражение CHECK |
| `businessRule` | `owner` entity либо relation; `text`; `enforcement=application\|trigger\|manual\|unspecified` | Инвариант, который не выражен доступными ограничениями |
| `index` | `owner` обяз. entity; `sqlName`; `method=btree`; `unique=false` | Обычный физический индекс |
| `indexPart` | `owner` обяз. index; `attribute` обяз.; `direction=asc\|desc`; `nulls=default\|first\|last`; `order` | Упорядоченная колонка индекса |

`sqlType` — каталог PostgreSQL: smallint, integer, bigint, numeric, real, doublePrecision, varchar, char, text, boolean, date, time, timestamp, timestamptz, uuid, bytea, json, jsonb. Для numeric precision/scale задаются числами отдельно; `varchar(80)` внутри sqlType не используется. Неизвестный пользовательский тип хранить через `sqlType=custom customType="имя"`, с предупреждением о непроверенной совместимости. Массивы, домены СУБД, ENUM СУБД, EXCLUDE и partial/expression indexes — расширение, нельзя автоматически терять их при будущем импорте.

Обычные составные B-tree индексы обязательны: в подготовленном model.json их 10, включая `product_id, observed_at DESC`. Порядок колонок и ASC/DESC сохраняются отдельными indexPart; индексы показываются в секции физической сущности и в свойствах. Индекс, автоматически обеспечивающий PK/UQ, отдельно не дублируется. Для FK в первом профиле targetKey ссылается только на key, не на произвольный index; ограничение профиля объявляется явно. Формирование CREATE INDEX сверяется с [PostgreSQL 18, CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html).

### 7.3. Смысл отношений и проверки

**ERD-04.** У `relation` параметры `toMin/toMax` означают число объектов `to` для одного объекта `from`; `fromMin/fromMax` — обратное. Маркер у конца `to` показывает `toMin/toMax`, у `from` — `fromMin/fromMax`. Это определение обязательно показать в свойствах, чтобы исключить перевёрнутые кратности.

**ERD-05.** FK направлен от дочерней таблицы к ключу родителя. На физическом листе линия крепится к строкам колонок и отображает состав пар. Самоссылка и несколько разных FK между теми же таблицами разрешены. Имена и маршруты таких связей независимы. Составной FK — одно ограничение, а не несколько отдельных FK.

**ERD-06.** Реляционные базовые правила: PK сочетает уникальность и запрет NULL; FK адресует подходящий уникальный ключ; составные ограничения учитывают весь набор колонок. CHECK не заменяет NOT NULL и не служит универсальной проверкой других строк/таблиц. При генерации DDL различать UNIQUE с обычной обработкой NULL и `NULLS NOT DISTINCT`. Основание: [PostgreSQL 18, Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).

**ERD-07.** Блокирующие коды: `ERD_MULTIPLE_PK`, `ERD_KEY_FOREIGN_ATTRIBUTE`, `ERD_FK_PAIR_MISMATCH`, `ERD_FK_TARGET_NOT_KEY`, `ERD_FK_TYPE_MISMATCH`, `ERD_PK_NULLABLE`, `ERD_DUPLICATE_SQL_NAME`, `ERD_INVALID_TYPE_PARAMETER`. Состав пар FK должен совпадать с полным targetKey по порядку и числу, без повторов. При неизвестном custom type вместо ложного подтверждения совместимости выдавать `ERD_TYPE_UNVERIFIED`.

**ERD-08.** Предупреждения: `ERD_NO_PK`, `ERD_TYPE_MISSING`, `ERD_RELATION_NOT_IMPLEMENTED`, `ERD_BUSINESS_RULE_UNENFORCED`, `ERD_FK_ACTION_CONFLICT`. `setNull` при NOT NULL и `setDefault` без пригодного default отмечать как конфликт проектного решения; не утверждать, что СУБД обязательно отвергнет само создание ограничения.

**ERD-09.** Логическая обязательность обратной стороны 1..many не следует из одного FK: наличие хотя бы одного ребёнка у каждого родителя требует отдельного правила. Кардинальность child→parent выводится из FK/nullable с учётом `match`; уникальность полного набора дочерних FK-колонок ограничивает parent→child максимум единицей. В остальных случаях показывать «не обеспечено ограничениями»; не придумывать проверку существования детей.

**ERD-10.** Идентифицирующая связь допустима в нашем профиле, когда перенесённый ключ родителя входит в PK дочерней сущности. many-to-many в логической модели допустима; физический лист сообщает, что требуется таблица связи. Мастер преобразования создаёт таблицу, два FK, ключи и новые отношения с preview. Нельзя скрыто менять модель при простом переключении листа.

**ERD-11.** Размеры varchar/char — положительные целые. Для первой поставки numeric допускает precision 1..1000 и scale 0..precision; прочие допустимые PostgreSQL-варианты помечаются как выход за локальный профиль, а не ошибка самой СУБД. Identity доступен для smallint/integer/bigint и несовместим с отдельно заданным default. Имена SQL сравниваются с учётом выбранного правила кавычек: экспорт всегда сохраняет точный регистр через экранированный идентификатор; не объединять разные имена эвристикой lower-case.

**ERD-12.** Для составного FK `match=simple` наличие NULL хотя бы в одной дочерней колонке допускает отсутствие соответствующей родительской строки; `match=full` допускает либо все NULL, либо полностью сопоставляемый набор. Редактор не рисует безусловное «ровно один родитель» для nullable-набора. Проверка готовности показывает отдельно логическое намерение и гарантии выбранных физических ограничений.

### 7.4. Ручное редактирование

**ERD-UI-01.** Двойной щелчок по пустой строке сущности добавляет атрибут. Inline-редактор: логическое/физическое имя, домен/тип, nullable; расширенные параметры — справа. Перетаскивание строки меняет order, ссылки по ID сохраняются.

**ERD-UI-02.** «Сделать PK/UQ» на нескольких выделенных строках создаёт key и keyPart. Существующий PK редактируется, второй не добавляется. При включении PK мастер явно предлагает снять nullable со всех участников одной операцией.

**ERD-UI-03.** Перетаскивание FK от дочерней колонки к родительскому ключу открывает сопоставление; для составного ключа — таблицу пар. Можно выбрать существующие дочерние колонки либо создать новые по образцу типов. Пользователь видит имена и действия ON DELETE/UPDATE до commit.

**ERD-UI-04.** Поддержать управление составом листа, «Показать соседние связи», скрытие неключевых атрибутов и полный режим. Скрытые атрибуты остаются в модели и исходнике. Если FK приходит к скрытой строке, показать свернутый якорь с именем поля и раскрытием, а не неверно прикреплять к другой строке.

**ERD-UI-05.** Смена SQL-типа показывает затронутые FK и не изменяет типы связанных колонок автоматически. Удаление колонки показывает ключи, FK и явно типизированные ссылки; произвольный текст CHECK не переписывается по совпадению слов и отмечается для пересмотра.

**ERD-UI-06.** Вкладка «Индексы» позволяет добавить индекс, выбрать колонки, переставить их и задать направление каждой. Все участники принадлежат одной entity; пустой индекс — незавершённость, чужая колонка — ошибка. Изменение имени индекса не меняет SQL-имена его таблицы и колонок. Удаление колонки показывает зависимые indexPart в каскаде.

### 7.6. DDL и готовность ERD

**ERD-DDL-01.** Обязательна детерминированная генерация PostgreSQL DDL из принятой физической модели в отдельный `.sql` после preview. SQL — результат экспорта, не язык редактора и не промежуточное хранилище. Автоматическое выполнение и подключение к серверу отсутствуют.

**ERD-DDL-02.** Идентификаторы экранируются как SQL-идентификаторы; выражения default/CHECK хранятся как явно введённый пользователем текст и не исполняются приложением. Неподдерживаемый тип/ограничение запрещает экспорт с заявлением «полный DDL»; нельзя молча пропустить строку. Сначала таблицы и ключи, затем FK через ALTER TABLE: циклические FK не препятствуют построению файла. Ошибочные бизнес-инварианты не превращать в выдуманный SQL.

**ERD-AC.** Из исходного `База_данных/model.json` и `schema.sql` перенесены все 29 таблиц/185 колонок, составные ключи, все FK и 10 обычных индексов. Десять листов ссылаются на общую модель. Переименование общей сущности отражается на обоих уровнях; скрытие атрибута не удаляет его из DDL; составной FK остаётся одним ограничением после сохранения, редактирования и повторного открытия. Индекс с DESC сохраняет порядок и направление в рисунке, коде и SQL.

## 8. Блок-схемы алгоритмов

### 8.1. Профиль и модель

Это самостоятельный профиль `NS-FLOWCHART-1`. Внешний вид опирается на привычные символы алгоритмических схем. [ISO 5807:1985](https://www.iso.org/standard/11955.html) определяет соответствующую область стандартизации; открытая карточка стандарта не подтверждает полное соответствие предлагаемого редактора. Формулировка «полностью по ГОСТ/ISO» без отдельной проверки недопустима.

| Тип | Поля | Отображение/смысл |
| --- | --- | --- |
| `algorithm` | `inputs`, `outputs`, `precondition`, `postcondition`, `description` — текст | Владелец алгоритма; не исполняемый код |
| `diagram` | `type=algorithm`, `algorithm` обяз. | Лист алгоритма |
| `start`, `end` | `owner` обяз. algorithm | Терминатор начала/завершения |
| `operation` | `owner`, `expression` | Прямоугольник; описание действия/формулы |
| `input`, `output` | `owner`, `data` — текст | Параллелограмм ввода/вывода |
| `decision` | `owner`, `expression`, `mode=binary\|multi` | Ромб с условием |
| `subroutine` | `owner`, `target` — algorithm либо отсутствие; `arguments`, `result` — текст | Предопределённый процесс; переход к алгоритму |
| `connector` | `owner`, `code` | Именованное соединение внутри листа |
| `offpage` | `owner`, `code` | Переход между листами одного алгоритма |
| `flow` | `from`, `to` обяз.; `guard`, `otherwise=false` | Направленный переход управления |
| `continuation` | `from`, `to` обяз. offpage | Семантическая пара межлистового перехода |

Все узлы принадлежат алгоритму; вложенность прямоугольников не меняет owner. Ссылка `subroutine.target` может указывать на другой algorithm того же документа. Рекурсия не запрещается, но помечается. Условия, формулы и аргументы не выполняются.

### 8.2. Правила и диагностика

**FLOW-01.** В готовом алгоритме один start и хотя бы один end; число end может быть больше одного. Это локальный учебный профиль. При построении отсутствие начала/конца — предупреждение, второй start — блокирующее противоречие профиля.

**FLOW-02.** В start нет входящих flow, в end нет исходящих. Обычная операция/input/output/subroutine имеет не более одного исходящего flow. Если нужно ветвление, используется decision. Несколько входов обычного узла допускаются как слияние альтернатив, а не как синхронизация параллельных ветвей.

**FLOW-03.** `decision mode=binary` имеет в готовой схеме две ветви; в multi — две или больше. Максимум одна ветвь `otherwise=true`; её label по умолчанию «Иначе». Для других ветвей нужны непустые guard либо понятные подписи. Редактор не доказывает взаимоисключение и полноту произвольных логических выражений.

**FLOW-04.** Цикл — обычная обратная связь flow, допустимая в графе. Найденный цикл без достижимого выхода даёт предупреждение «возможный бесконечный цикл», а не доказательство бесконечности. Достижимость вычисляется структурно без исполнения guard.

**FLOW-05.** Между разными algorithm прямой flow запрещён. Между листами одного алгоритма сохраняется пара offpage/continuation; у каждого выхода ровно одно продолжение, совпадающие code без явной связи не объединяются. Переход открывает целевой лист и его маркер.

**FLOW-06.** Коды: `FLOW_WRONG_OWNER`, `FLOW_START_INCOMING`, `FLOW_END_OUTGOING`, `FLOW_BRANCH_REQUIRES_DECISION`, `FLOW_TOO_MANY_STARTS`, `FLOW_MULTIPLE_DEFAULTS` блокируют противоречие. `FLOW_NO_START`, `FLOW_NO_END`, `FLOW_UNREACHABLE`, `FLOW_INCOMPLETE_DECISION`, `FLOW_UNRESOLVED_SUBROUTINE`, `FLOW_CYCLE_WITHOUT_EXIT` — предупреждения готовности.

### 8.3. Ручной и кодовый редакторы

**FLOW-UI-01.** Палитра разделена на шаги, ветвление, начало/конец, соединители и примечания. Выбор default/guard доступен на стрелке. Команда «Вставить шаг в связь» заменяет один flow двумя, переносит условие на первый участок и фиксирует изменение одной операцией.

**FLOW-UI-02.** Для нового decision мастер создаёт две подписанные ветви к выбранным существующим узлам либо предлагает добавить продолжения. До выбора целей нет фиктивных скрытых узлов. Ветви по возможности разводятся по разным сторонам ромба.

**FLOW-UI-03.** Смена типа фигуры проверяет число исходящих связей. Decision с тремя ветвями нельзя превратить в operation без явного выбора, какие связи убрать/перенести. Панель показывает входы/выходы, формулу, целевой алгоритм и нарушения готовности.

**FLOW-UI-04.** Автораскладка сверху вниз с отдельными коридорами возврата. Направление схемы — настройка листа; смысл flow не зависит от направления рисунка. Ветка «Да» не обязана всегда быть справа: расположение остаётся редактируемым.

```text
flowchart pricing "Расчёт цены карточки"
algorithm calc "Расчёт цены и массы" inputs="Версия BOM и предложения" outputs="Цена и масса"
diagram main Алгоритм type=algorithm algorithm=calc
start begin Начало owner=calc
input load "Получить состав BOM" owner=calc data="Слоты и выбранные предложения"
decision valid "Все слоты разрешены?" owner=calc mode=binary expression="unresolvedSlots == 0"
operation sum "Рассчитать себестоимость" owner=calc expression="cost = sum(quantity * offerPrice)"
output error "Вернуть список проблем" owner=calc data="Неразрешённые слоты"
end done Конец owner=calc
flow f1 "" from=begin to=load
flow f2 "" from=load to=valid
flow f3 Да from=valid to=sum guard="unresolvedSlots == 0"
flow f4 Нет from=valid to=error otherwise=true
flow f5 "" from=sum to=done
flow f6 "" from=error to=done
view vb "" diagram=main element=begin
view vl "" diagram=main element=load
view vv "" diagram=main element=valid
view vs "" diagram=main element=sum
view ve "" diagram=main element=error
view vd "" diagram=main element=done
view vf1 "" diagram=main element=f1 from=vb to=vl
view vf2 "" diagram=main element=f2 from=vl to=vv
view vf3 "" diagram=main element=f3 from=vv to=vs
view vf4 "" diagram=main element=f4 from=vv to=ve
view vf5 "" diagram=main element=f5 from=vs to=vd
view vf6 "" diagram=main element=f6 from=ve to=vd
```

**FLOW-AC.** Перенести три алгоритма РОП с реальными решениями и возвратами. Смена подписи не меняет guard; вставка шага сохраняет направление; ошибочная ссылка в коде не разрушает принятый граф; loop и offpage переживают повторное открытие.

## 9. Дерево функций

### 9.1. Семантика и язык

**TREE-01.** Дерево описывает декомпозицию функций, а не порядок исполнения. Связь родитель→ребёнок означает «состоит из подфункции». Стрелки данных, guard и последовательность действий не добавляются в эту нотацию.

| Тип | Поля | Правило |
| --- | --- | --- |
| `function` | `parent` — function; `order`; `description`; `code` — необязательный пользовательский код | Не более одного родителя |
| `diagram` | `type=tree`, `root` обяз. function | Показываемое поддерево |
| `reference` | `owner` обяз. function; `document`, `element`, `kind=requirement\|idef0\|other` | Справочная связь с источником; не второй родитель |
| `view` | общий контракт | Отображение функции |

Рёбра дерева вычисляются из `function.parent` и отображений, отдельный дублирующий `edge` не хранится. Геометрия вычисленного ребра имеет стабильный ключ по view ребёнка. В source и JSON один источник истины для иерархии.

**TREE-02.** В полном документе готовое дерево имеет один корень. Лес из временно не присоединённых функций допускается с предупреждением; циклы и ссылка на себя блокируются. Корневой лист не обязан показывать все уровни, но предупреждает о скрытых ветвях.

**TREE-03.** Отображаемая нумерация, например 0, 1, 1.1, 1.2, выводится из порядка братьев и выбранного корня/режима листа. Она не является ID. `code`, если задан, показывается как отдельный стабильный код; изменение положения не переписывает его.

### 9.2. Ручные команды

**TREE-UI-01.** «Добавить дочернюю», «Добавить соседнюю», «Переместить ветвь», «Поднять уровень», «Опустить уровень», «Открыть поддерево», «Свернуть/развернуть». Перенос ветви обновляет parent/order один раз и показывает новое место до отпускания.

**TREE-UI-02.** Удаление функции из модели предлагает два конкретных действия: удалить поддерево либо поднять детей к прежнему родителю с preview порядка. Для корня с несколькими детьми нельзя молча выбрать нового корня. Удаление view не меняет parent.

**TREE-UI-03.** Раскладка сверху вниз и слева направо; интервал, число видимых уровней и свёрнутость — параметры вида. Размер карточек учитывает многострочные названия. Общий шрифт и чёрно-белый режим обеспечивают читаемость печати.

**TREE-UI-04.** Дополнительная команда «Создать дерево из IDEF0» строит копию иерархии функций по принятой модели `.omni`. Источник и fingerprint сохраняются как происхождение; последующие изменения не сливаются автоматически. «Обновить из источника» показывает различия и сохраняет ручные подписи/геометрию либо явно отмечает конфликт. Для основной приёмки достаточно ручного переноса D01; автоматическое обновление — расширение.

```text
functree functions "Функции системы карточек"
function root "Управлять карточками компьютерных систем" order=0
function bom "Управлять составом BOM" parent=root order=0
function offers "Обновлять предложения" parent=root order=1
function publish "Публиковать карточки" parent=root order=2
function replace "Выполнять массовую замену" parent=bom order=0
diagram overview "Дерево функций" type=tree root=root
view vr "" diagram=overview element=root
view vb "" diagram=overview element=bom
view vo "" diagram=overview element=offers
view vp "" diagram=overview element=publish
view vx "" diagram=overview element=replace
```

**TREE-VAL.** `TREE_CYCLE`, `TREE_BAD_PARENT` блокируют; `TREE_MULTIPLE_ROOTS`, `TREE_EMPTY_FUNCTION`, `TREE_DUPLICATE_ORDER`, `TREE_EXTERNAL_SOURCE_STALE` предупреждают. Одинаковые названия функций допустимы; одинаковые ID — нет.

**TREE-AC.** Дерево D01 строится мышью и кодом. Перенос поддерева обновляет нумерацию, сохраняет ID и собственные связи; Undo возвращает всё поддерево. Сохранение свёрнутого вида не удаляет потомков.

## 10. Общие схемы, кодирование и инфраструктура

### 10.1. Границы редактора

SCHEME — честно обозначенный редактор свободных структурных схем с несколькими локальными профилями. Он не выдаёт произвольный прямоугольник за UML Component и не подменяет ERD/Activity. Общие фигуры допустимы здесь, поскольку их смысл задаётся автором схемы.

| Тип | Поля | Вид |
| --- | --- | --- |
| `block` | `shape=rectangle\|rounded\|ellipse\|diamond\|cylinder\|document\|cloud`, `description` | Блок |
| `container` | `description` | Содержательный контейнер/зона |
| `member` | `owner` обяз. container; `element` обяз. block/container | Явное включение в зону, без циклов |
| `label` | `text` | Свободный текст |
| `link` | `from`, `to`; `kind=association\|directed\|bidirectional`; `description` | Именованная связь |
| `codePattern` | `description` | Структура составного кода |
| `segment` | `owner` обяз. codePattern; `kind=literal\|counter\|value`; `literal`, `width`, `alphabet=digits\|latin\|any`, `example`, `meaning`, `order` | Часть кода |
| `diagram` | `type=general\|coding\|infrastructure\|access` | Лист/профиль |

**SCHEME-01.** Разрешить схему любого из четырёх профилей в одном SCHEME-документе. Палитра активного листа показывает относящиеся к нему шаблоны, а инспектор не теряет декларации других листов. Цвет, толщина, dashed и наконечники — оформление view; `kind` задаёт направленность связи, которую оформление не может опровергать.

**SCHEME-02.** Для инфраструктуры добавить поля block `role=client|gateway|application|database|storage|external|generic`, `technology`, `version`, `resources`; link `protocol`, `port`, `purpose`; container `zone=public|dmz|internal|generic`. Это локальные подписи, не модель развёртывания UML и не реально настроенная сеть. Порт — число 1..65535 либо пустое; список портов задаётся отдельными связями/описанием, не неподтверждённым синтаксисом.

**SCHEME-03.** Для доступа добавить block `role=principal|authentication|authorization|operation|deny|audit|generic`, `policy` — текст. Модель отображает решение RBAC, но не вычисляет разрешения и не заявляет безопасность системы. Таблица CRUDX остаётся отдельным артефактом отчёта; полноценный редактор политик не нужен.

Каталог допустимых role у SCHEME является объединением ролей профилей. Палитра/шаблон листа лишь предлагает подходящие значения и не делает существующие элементы других листов ошибочными. Несколько member для одного элемента в разных зонах в первом профиле не допускаются; для визуального дублирования используются views, а не противоречивое членство.

### 10.2. Схема кодирования

**CODEPATTERN-01.** Сегменты показываются последовательно с направляющими/выносками к пояснениям. `literal` печатается буквально; `counter` показывает ширину и ведущие нули на примере; `value` — условный фрагмент указанной длины/алфавита. Программа не выдаёт реальные номера BOM и не поддерживает общий счётчик предприятия.

**CODEPATTERN-02.** Кнопка «Показать пример» собирает строку из `literal`/`example`. Значение не соответствует ширине/алфавиту — предупреждение; отрицательная/нулевая заданная width — ошибка. Для literal ширина выводится из символов, отдельное противоречивое значение не принимается.

**CODEPATTERN-03.** В UI можно добавлять и переставлять сегменты, менять значение и пояснение. Перестановка изменяет order и превью. Для каждого сегмента доступна независимая позиция выноски в layout, но не независимое значение скопированной подписи.

```text
scheme coding "Кодирование BOM"
diagram main "Схема кода" type=coding
codePattern bom_code "Код BOM" description="Префикс и порядковый номер"
segment prefix Префикс owner=bom_code kind=literal literal=BOM meaning="Тип объекта" order=0
segment separator Разделитель owner=bom_code kind=literal literal="-" order=1
segment number Номер owner=bom_code kind=counter width=6 alphabet=digits example=000123 meaning="Порядковый номер BOM" order=2
view code_view "" diagram=main element=bom_code
```

### 10.3. Редактирование и готовность

**SCHEME-UI-01.** Свободные блоки, текст и связи; выравнивание, размер, группировка views, порядок наложения, контейнеры и печать. Действия «Сгруппировать для перемещения» и «Включить в зону» различаются: первое — layout, второе — member в source.

**SCHEME-UI-02.** Ручной выбор цвета не создаёт новую семантическую роль. Профиль access предлагает заготовку «Пользователь → Аутентификация → Проверка прав → Разрешено/Отказ», но не запрещает другую структуру. Проверяется только целостность графа и специальные параметры.

**SCHEME-VAL.** Блокирующие: `SCHEME_BAD_ENDPOINT`, `SCHEME_MEMBERSHIP_CYCLE`, `SCHEME_INVALID_PORT`, `CODEPATTERN_INVALID_WIDTH`. Предупреждения: отсутствие подписи, пересечения, неполный пример, неизвестный протокол. Изолированный текст/блок допустим в общей схеме.

**SCHEME-AC.** D04, D10 и D24 строятся без вставки готового SVG. Смена свойства блока обновляет подпись, source и сохранённую модель; перенос визуальной группы не меняет membership; код BOM собирается из редактируемых сегментов.

## 11. UML Component

### 11.1. Семантический профиль

Добавить `component` к UML diagramKinds и расширить существующий общий профиль. Component, интерфейс, порт и часть — разные сущности. Один компонент допускает отображения на компонентном и deployment-листах; один интерфейс может использоваться несколькими компонентами.

Нормативный ориентир: OMG UML 2.5.1, §10.4 и §11.2–11.6. В предлагаемой первой реализации поддерживается явный набор ниже, а не вся метамодель структурных классификаторов.

| Тип | Поля | Смысл |
| --- | --- | --- |
| `component` | `abstract=false`, `description` | Тип компонента |
| `interface` | существующие поля/операции UML | Контракт; переиспользуется |
| `part` | `owner` обяз. component; `classifier` обяз. component; `lower=1`, `upper=1` | Часть внутренней структуры, типизированная компонентом |
| `port` | `owner` обяз. component; `classifier` — interface; `conjugated=false` | Порт на границе типа компонента |
| `interfaceUse` | `owner` обяз. component либо port; `interface` обяз.; `direction=provided\|required` | Наше явное представление предоставления/потребности |
| `usage` | `from` component; `to` interface | Использование интерфейса без порта |
| `realization` | расширить допустимый from существующей связи на component; `to` interface | Реализация интерфейса |
| `dependency` | существующая связь, расширить виды концов на component/artifact | Зависимость, не канал исполнения |
| `componentConnector` | `owner` обяз. component; `kind=assembly\|delegation` | Двоичный connector внутренней структуры |
| `componentEnd` | `owner` обяз. componentConnector; `part` необяз.; `port` обяз.; `order=0\|1` | Конец на внешнем порте owner либо порте типа части |

`componentConnector` намеренно имеет отдельное имя, чтобы не изменить существующий `connector` коммуникации. Конец с part ссылается на порт classifier этой части, без part — на порт владельца connector. Нельзя соединять два рисунка без структурного контекста и сохранять это как полноценный UML Connector. Простая диаграмма зависимостей компонентов не требует искусственного контейнера; для assembly/delegation нужен компонент-композиция и его части.

### 11.2. Правила

**COMP-01.** `interfaceUse` — локальная каноническая запись. Для прямой realization/usage редактор вычисляет эффективные provided/required. Если пользователь создаёт интерфейс визуальным «шариком/розеткой», команда записывает согласованную каноническую форму; два независимых источника одного и того же факта не допускаются. Допускается модель realization/usage без interfaceUse, но её эффективный интерфейс не дублируется в projection.

**COMP-02.** Первая поставка поддерживает только simple port: один interface classifier и одно эффективное направление. Без conjugated такой типизированный порт предоставляет интерфейс; `conjugated=true` меняет направление на требуемое. Если задан interfaceUse для порта, его interface/direction должны совпадать с этим результатом; UI меняет связанные поля одной транзакцией, противоречивый код блокируется. Порты с составными наборами предоставляемых/требуемых интерфейсов — расширение: их нельзя молча изображать как простой ball-and-socket. Локальный каталог интерфейсов не проверяет программную реализацию API.

**COMP-03.** Assembly в первом профиле соединяет требуемый и предоставляемый простые порты частей одного владельца с одинаковым interface ID. Это намеренно ограниченный профиль; полная UML-совместимость типов/подтипов не заявляется. Delegation соединяет внешний порт владельца и совместимый порт его внутренней части с согласованным направлением обслуживания.

**COMP-04.** Перемещение view части в другую рамку не меняет `part.owner`. «Перенести часть в компонент» — отдельная команда с проверкой connector и зависимостей. Port хранит семантического owner, а положение вдоль границы — layout. Вложение вида component не заменяет part.

**COMP-05.** Нельзя считать цикл dependency ошибкой стандарта. Допускаются циклические зависимости с предупреждением качества. Цикл семантического владения блокируется. Рекурсивные типы частей не разворачиваются бесконечно: отображение имеет явный предел раскрытия.

### 11.3. Ручной и кодовый редакторы

**COMP-UI-01.** Палитра: компонент, интерфейс, часть, порт, предоставляемый/требуемый интерфейс, dependency, usage/realization, assembly/delegation, примечание. Компонент рисуется со знаком компонента или явной меткой «component»; интерфейс — прямоугольником либо шариком/розеткой согласно связи, переключение вида не создаёт другой интерфейс.

**COMP-UI-02.** Команда «Добавить порт» выбирает компонент и интерфейс, затем сторону/место. «Добавить часть» предлагает существующий тип компонента или создаёт новый. При рисовании connector мастер подставляет владельца и предлагает только порты допустимых частей.

**COMP-UI-03.** Перенос порта по периметру сохраняет owner и connector. Изменение interface показывает все затронутые связи. Удаление порта перечисляет componentEnd/interfaceUse и связанные views; без подтверждённого каскада исходная модель сохраняется.

```text
uml architecture "Архитектура карточек"
diagram components "Компоненты" type=component
component ui "Веб-интерфейс"
component bom "Управление BOM"
component publication Публикации
interface cardApi "API карточек"
realization provide "" from=bom to=cardApi
usage consume "" from=ui to=cardApi
dependency publishBom "Получить версию BOM" from=publication to=bom
view ui_v "" diagram=components element=ui
view bom_v "" diagram=components element=bom
view publication_v "" diagram=components element=publication
view api_v "" diagram=components element=cardApi
view provide_v "" diagram=components element=provide from=bom_v to=api_v
view consume_v "" diagram=components element=consume from=ui_v to=api_v
view dependency_v "" diagram=components element=publishBom from=publication_v to=bom_v
```

Для составной структуры минимальная семантическая вставка в тот же документ:

```text
component system "Система карточек"
part web_part web owner=system classifier=ui lower=1 upper=1
part bom_part bom owner=system classifier=bom lower=1 upper=1
port ui_port api owner=ui classifier=cardApi conjugated=true
port bom_port api owner=bom classifier=cardApi
interfaceUse ui_need "" owner=ui_port interface=cardApi direction=required
interfaceUse bom_provide "" owner=bom_port interface=cardApi direction=provided
componentConnector assembly "Связь частей" owner=system kind=assembly
componentEnd assembly_client "" owner=assembly part=web_part port=ui_port order=0
componentEnd assembly_server "" owner=assembly part=bom_part port=bom_port order=1
```

Эта вставка описывает модель; чтобы увидеть части и connector, команда показа создаёт views частей, портов и отношения. Отсутствие views является информацией, не потерей данных.

**COMP-VAL.** Блокируют `UML_COMP_OWNER`, `UML_COMP_END_COUNT`, `UML_COMP_PORT_TYPE`, `UML_COMP_INTERFACE_MISMATCH`, `UML_COMP_CONNECTOR_CONTEXT`. Предупреждают `UML_COMP_UNUSED_PORT`, `UML_COMP_REQUIRED_UNBOUND`, `UML_COMP_CYCLIC_DEPENDENCY`. Не подключённый внешний порт допустим для промежуточной архитектуры; готовность определяется выбранной границей системы.

**COMP-AC.** D02 переносится как настоящие component/dependency. Дополнительно приёмочный пример демонстрирует interface, part, порты, assembly и delegation; нет смешения с connector коммуникации и утраты старых четырёх UML-видов.

## 12. UML Activity

### 12.1. Объём

Добавить `activity` к UML diagramKinds. Это модель управления и передачи объектов внутри Activity. Не использовать внутри неё BPMN gateway/event либо FLOWCHART operation как общую предметную сущность. Геометрические примитивы могут переиспользоваться, семантические типы — раздельные.

Нормативный ориентир: OMG UML 2.5.1, §15–16. Для первой поставки вводится ограниченный профиль действий/потоков без исполнения токенов, обработки исключений и прерываемых областей.

| Тип | Поля | Назначение |
| --- | --- | --- |
| `activity` | `description`, `precondition`, `postcondition` | Владелец поведения |
| `diagram` | `type=activity`, `activity` обяз. | Лист активности |
| `action` | `owner` обяз. activity; `kind=opaque\|callBehavior`; `behavior` — activity для callBehavior; `body` — текст | Действие |
| `initial`, `activityFinal`, `flowFinal`, `merge`, `fork`, `join`, `decision` | `owner` обяз. activity; decision: `decisionInput`; join: `joinSpec` | Управляющие узлы |
| `objectNode` | `owner` activity; `classifier` — существующий UML-классификатор; `state` | Объект/данные |
| `inputPin`, `outputPin` | `owner` обяз. action; `classifier`; `lower=1`, `upper=1` | Вход/выход действия |
| `controlFlow` | `owner` activity; `from`, `to`; `guard` | Поток управления |
| `objectFlow` | `owner` activity; `from`, `to`; `guard` | Поток объектов |
| `partition` | `owner` activity; `represents` — существующая модельная сущность; `parent` — partition той же activity | Дорожка/группа ответственности |
| `partitionMember` | `owner` partition; `element` — узел или поток данной activity | Членство, отдельно от владения |

`diagram.activity` не конфликтует с существующим `diagram.interaction`. Узлы принадлежат Activity, а не дорожке. В первой поставке одна система непересекающихся дорожек и максимум одна leaf-partition для узла; несколько измерений partition — расширение. Это локальное ограничение визуального профиля, не общий запрет UML.

### 12.2. Семантика и таблица соединений

**ACT-01.** ActivityFinal завершает текущее выполнение Activity; FlowFinal завершает достигший его поток. Decision выбирает продолжение, Merge объединяет альтернативы, Fork разделяет поток, Join синхронизирует. Различия влияют на форму, тип и проверки, а не только на подпись. Основание: [OMG UML 2.5.1, §15](https://www.omg.org/spec/UML/2.5.1/PDF).

| Узел | ControlFlow | ObjectFlow | Ограничение первого профиля |
| --- | --- | --- | --- |
| initial | Только исходящие | Нет | Входящие запрещены |
| action | Входящие/исходящие | Через pins | Нет скрытого преобразования objectFlow в controlFlow |
| inputPin | Нет | Входящий | Относится к action; вывод из inputPin не поддержан |
| outputPin | Нет | Исходящий | Относится к action; ввод в outputPin не поддержан |
| objectNode | Нет | Входящий/исходящий | Прямой controlFlow запрещён |
| decision | Вход/выход одного вида | Вход/выход одного вида | Один основной вход в первом профиле; decisionInputFlow — расширение |
| merge | Несколько входов, один выход | Несколько входов, один выход | На одном узле однородный вид потока |
| fork | Один вход, несколько выходов | Один вход, несколько выходов | Однородный вид потока |
| join | Несколько входов, один выход | Несколько входов, один выход | Первый профиль — однородные потоки, joinSpec по умолчанию and |
| activityFinal, flowFinal | Только входящие | Только входящие | Исходящие запрещены |

**ACT-02.** Не объявлять требование «ровно одна initial на Activity» общим UML-правилом. Несколько initial допустимы и не означают альтернативный выбор. Для конкретного учебного шаблона предлагать одну. Отсутствие initial само по себе не всегда делает UML Activity неверной; в нашем учебном профиле это предупреждение готовности с учётом входных объектных узлов.

**ACT-03.** На выходах decision допускается максимум один `guard=else`. Guards хранятся как выражения; не выполняются и не доказываются взаимоисключающими. Merge нельзя трактовать как Join; заменять тип только после проверки текущих концов и объяснения изменения смысла.

**ACT-04.** ObjectFlow проверяет совместимость известных classifier концов в поддержанном профиле: одинаковый ID либо явно разрешённая существующая иерархия generalization. При отсутствующем типе — предупреждение. ControlFlow не переносит тип объекта.

**ACT-05.** Прямые потоки между разными activity запрещены. CallBehaviorAction ссылается на Activity без автоматического разворачивания; входные/выходные pins редактируются явно. Рекурсивный вызов — предупреждение, не бесконечное раскрытие листов.

### 12.3. Ручной и кодовый редакторы

**ACT-UI-01.** В палитре отдельно управляющие узлы, действия, данные, дорожки и два типа потоков. Контекстная команда добавляет pin к выбранному action, предлагает classifier и кратность. Pins остаются на границе action при resize; их порядок/тип находятся в модели, положение — layout.

**ACT-UI-02.** Создание/перенос дорожки меняет только её view. Drop узла в дорожку через режим «Назначить ответственность» меняет partitionMember и view parent одной транзакцией. Перемещение прямоугольника поверх дорожки без этого режима не присваивает роль молча.

**ACT-UI-03.** Fork/Join рисуются полосой, Decision/Merge — ромбом, два final имеют различимые символы. Инспектор всегда показывает точный тип. Схема с параллельными ветвями должна оставаться читаемой в чёрно-белом PNG/PDF.

```text
uml preparation "Подготовка карточки"
```

**ACT-VAL.** Блокируют `UML_ACT_WRONG_OWNER`, `UML_ACT_ENDPOINT_KIND`, `UML_ACT_FINAL_OUTGOING`, `UML_ACT_INITIAL_INCOMING`, `UML_ACT_MULTIPLE_ELSE`, `UML_ACT_FLOW_TYPE_CONFLICT`. Нехватка ветвей, неуказанные guards/типы, изоляция и неполные pins — предупреждения. Неподдержанная decisionInputFlow явно отклоняется как выход за профиль, а не объявляется ошибкой UML вообще.

**ACT-AC.** D06 переносится как Activity. Дополнительный пример содержит параллельные ветви, Join, ObjectFlow, pins и FlowFinal, чтобы готовность не подтверждалась только простой цепочкой. Замена Merge↔Join меняет семантический тип и диагностику; Undo восстанавливает исходный тип и связи.

## 13. UML Deployment

### 13.1. Модель

Добавить `deployment` к UML diagramKinds. Первый профиль описывает типы узлов/сред/артефактов; поддержка экземпляров InstanceSpecification/Slot относится к будущему редактору объектов. Не подменять развёртывание перечнем серверов с текстом внутри.

| Тип | Поля | Назначение |
| --- | --- | --- |
| `node` | `owner` необяз. node/device/executionEnvironment; `description` | Вычислительный узел |
| `device` | как node; `hardware` — локальная аннотация | Физическое устройство |
| `executionEnvironment` | как node; `technology`, `version` — локальные аннотации | Среда исполнения |
| `artifact` | `owner` необяз. artifact; `fileName`, `version` | Артефакт, не компонент |
| `deployment` | `location` обяз. node/device/executionEnvironment; `artifact` обяз. artifact | Размещение одного артефакта в одном target в нашем двоичном профиле |
| `manifestation` | `from` обяз. artifact; `to` обяз. component либо другой поддержанный packageable classifier | Какой модельный элемент воплощён артефактом |
| `communicationPath` | `from`, `to` обяз. node/device/executionEnvironment; `protocol`, `port` — локальные аннотации | Канал связи, по умолчанию ненаправленный |
| `deploymentSetting` | `owner` обяз. deployment; `key`, `value` — текст | Локальные параметры развёртывания, не полноценный UML DeploymentSpecification |

`deploymentSetting` именуется локальным расширением и не рисуется как стандартный DeploymentSpecification без реализации его ограничений. Поддержка полноценного DeploymentSpecification — расширение. Технические характеристики узлов и протоколы не выполняются и не проверяют наличие реальных ресурсов.

### 13.2. Отношения и направления

**DEP-01.** Размещение связывает target и artifact; manifestation — artifact и реализуемый им компонент. Для одного компонента возможно несколько артефактов, один артефакт допускает несколько размещений. Дублировать компонент для каждого сервера нельзя, если это всё ещё один модельный тип.

**DEP-02.** В UML Deployment location является client, deployed artifact — supplier; при стрелочном виде зависимость «deploy» направлена **от узла к артефакту**. Manifestation направлена **от артефакта к компоненту**. Не определять направление по бытовой фразе «отправить файл на сервер». Основание: OMG UML 2.5.1, §19.5.4 и §19.5.9; PDF-страницы 703–706.

**DEP-03.** Вложенный вид артефакта в узле может отображать существующий deployment. Явная команда «Разместить артефакт здесь» создаёт deployment и view parent; просто перемещение фигуры внутрь рамки не создаёт отношения автоматически. Для показа одного artifact на двух узлах создаются два views и два deployment.

**DEP-04.** Семантическая вложенность node определяется `owner`; вложенный artifact не становится `owner=node`, поскольку размещение — отдельное отношение. Контейнер layout может представлять окружение, но отсутствие view не удаляет deployment.

**DEP-05.** CommunicationPath соединяет только deployment targets; интерфейс, компонент и файл не подходят. Протокол и порт принадлежат аннотации пути, а не меняют тип стрелки. Для направленного вызова сервиса использовать другую подходящую диаграмму либо отдельную текстовую аннотацию, не называть обычный directed arrow CommunicationPath.

### 13.3. Ручное и кодовое редактирование

**DEP-UI-01.** Палитра: узел, устройство, среда, артефакт, существующий компонент, deployment, manifestation, communicationPath и примечание. Формы узнаваемые: узел с объёмной рамкой, артефакт со значком файла, среда с обозначением типа. Рисунок должен оставаться плоско читаемым при экспорте.

**DEP-UI-02.** «Добавить среду внутри узла» одновременно создаёт owner и views. «Разместить артефакт» предлагает существующий artifact/новый; «Показать воплощаемые компоненты» добавляет их views без копирования модели. Перетаскивание узла переносит вложенные виды и привязки путей.

**DEP-UI-03.** Удаление узла показывает дочерние node и deployments; artifact, размещённый также на другом узле, не удаляется автоматически. Снять deployment можно без удаления artifact. Изменение пути к файлу — изменение `fileName`, не чтение файла и не запуск программы.

```text
uml deploymentModel "Развёртывание системы карточек"
diagram infrastructure Развёртывание type=deployment
device server "Прикладной сервер" hardware="4 vCPU и 8 GB RAM — проектное значение"
executionEnvironment runtime "JRE 21" owner=server technology=JRE version=21
artifact app "Приложение карточек" fileName=cards.jar
component backend "Прикладная подсистема"
deployment deployApp "Разместить приложение" location=runtime artifact=app
manifestation appImplements "" from=app to=backend
device database "Сервер БД"
communicationPath sql "Доступ к БД" from=server to=database protocol=PostgreSQL port=5432
view server_v "" diagram=infrastructure element=server
view runtime_v "" diagram=infrastructure element=runtime parent=server_v
view app_v "" diagram=infrastructure element=app parent=runtime_v
view backend_v "" diagram=infrastructure element=backend
view database_v "" diagram=infrastructure element=database
view deploy_v "" diagram=infrastructure element=deployApp from=runtime_v to=app_v
view manifest_v "" diagram=infrastructure element=appImplements from=app_v to=backend_v
view sql_v "" diagram=infrastructure element=sql from=server_v to=database_v
```

Визуальный режим может скрыть стрелку deploy, если вложение однозначно её показывает; само отношение остаётся в source, инспекторе и модели. При неоднозначном вложении скрытие запрещено либо требуется явная подпись размещения.

**DEP-VAL.** Блокируют `UML_DEP_BAD_TARGET`, `UML_DEP_BAD_ARTIFACT`, `UML_DEP_OWNER_CYCLE`, `UML_DEP_BAD_COMMUNICATION_END`, `UML_DEP_WRONG_MANIFESTATION_END`. Предупреждают неразмещённый артефакт, неподписанный путь и несогласованное визуальное вложение. Отсутствие реального сервера не является ошибкой диаграммы.

**DEP-AC.** D21 переносится с различением узлов, сред, артефактов и компонентов. Один artifact размещается в двух средах без дублирования сущности. После удаления одного deployment второе размещение и manifestation сохраняются. Направления deploy/manifest проверены отдельно.

## 14. Каркасные интерфейсы

### 14.1. Назначение и границы

**WIRE-01.** WIREFRAME моделирует структуру экрана, элементы ввода, таблицы и переходы. Результат — собственная редактируемая модель каркаса, а не HTML-приложение. Не требуются CSS-редактор, генератор рабочего фронтенда, реальная авторизация, сетевые запросы, адаптивная вёрстка и библиотека произвольных дизайн-систем.

**WIRE-02.** Обязательные экраны варианта: список карточек; редактор версии BOM; предложения и сопоставления; массовая замена; карточка и публикация; журнал публикаций и уведомлений. Общие элементы можно копировать с новыми ID. Reusable components с наследованием и overrides — расширение.

### 14.2. Декларации

| Тип | Поля | Правило |
| --- | --- | --- |
| `screen` | `description`, `role` — текст о пользователе, `initial=false` | Экран; один initial на прототип |
| `diagram` | `type=screen\|navigation`, `screen` обяз. для screen | Экранный лист либо карта переходов |
| `widget` | `owner` обяз. screen/контейнерный widget; `type`; `order`; `state=normal\|disabled\|error\|loading\|hidden`; `required=false`; `value`, `placeholder`, `help` | Элемент интерфейса |
| `option` | `owner` обяз. widget соответствующего типа; `value`, `selected=false`, `order` | Вариант выбора/вкладка |
| `tableColumn` | `owner` обяз. widget type=table; `key`; `dataType=text\|number\|date\|boolean\|status`; `order` | Столбец |
| `tableRow` | `owner` обяз. widget type=table; `order` | Демонстрационная строка |
| `tableCell` | `owner` обяз. tableRow; `column` обяз. tableColumn; `value` | Ячейка того же table |
| `uiAction` | `owner` обяз. widget; `event=click\|submit\|change`; `kind=navigate\|openModal\|closeModal\|toggle`; `target` | Локальный переход/действие прототипа |
| `binding` | `owner` обяз. widget/column; `document`, `element`, `description` | Справочное сопоставление с моделью данных, без запроса к БД |

Каталог обязательных widget.type: `panel`, `text`, `heading`, `input`, `textarea`, `number`, `select`, `checkbox`, `radioGroup`, `button`, `table`, `tabs`, `tabPanel`, `toolbar`, `sidebar`, `badge`, `alert`, `imagePlaceholder`, `modal`. Изображение-заглушка достаточно для приёмки, произвольные сетевые картинки не нужны.

Контейнерные типы: panel, tabPanel, toolbar, sidebar, modal. Tabs содержит option, а каждый tabPanel имеет обязательный `tab` — ссылку на option этого tabs; визуальные панели принадлежат общей экранной/контейнерной области. Table содержит только column/row/cell как модельные части, произвольные widget внутрь таблицы не помещаются в первом профиле.

Для input/number/textarea/select/checkbox/radioGroup допустимы `value`, `required`, `placeholder` по смыслу типа. Для button — label и state; для text/heading — `text`; для alert — `tone=info|success|warning|error`. Метаданные не предлагают бессмысленное `required` для заголовка. Скрытые неиспользуемые поля прежнего типа сохранять только при явной поддержке перехода; при смене типа показать список удаляемых полей.

### 14.3. Ручной редактор

**WIRE-UI-01.** Экран — фиксированная область с размером в layout. Палитра предлагает контролы; drag показывает выравнивание и допустимый owner. По умолчанию свободная раскладка; контейнеру можно задать визуальный режим vertical/horizontal с gap/padding и закреплением. Эти параметры находятся в layout, не в семантическом source.

**WIRE-UI-02.** Изменение ширины поля не меняет лимит вводимых данных. Размер таблицы не меняет число столбцов. Добавление столбца/строки создаёт декларации, resize столбца меняет layout по column ID. При сортировке демонстрационных строк меняется order, а не реальные данные приложения.

**WIRE-UI-03.** Панель свойств содержит название, тип, состояние, обязательность, подсказку, демозначение и переход. Пользователь может задать состояние error/disabled/loading как свойство каркаса. Это дизайнерское описание, не результат реального серверного процесса.

**WIRE-UI-04.** Режим «Редактирование» выбирает контролы. Режим «Просмотр прототипа» выполняет только разрешённые локальные uiAction и временное переключение tabs/options. Никаких JavaScript/eval, внешних URL или HTTP-запросов. Выход из preview сбрасывает временные значения и не записывает их в source, кроме явной команды «Принять демонстрационные значения».

**WIRE-UI-05.** `navigate` ведёт на screen; `openModal`/`closeModal` — на widget type=modal текущего экрана; `toggle` — на widget текущего экрана. Для disabled нет активного действия. `submit` не вызывает сервер: допустим только явно заданный локальный переход. Состояние прототипа живёт отдельно от истории проектирования.

**WIRE-UI-06.** Карта навигации рисует screen как карточки, uiAction navigate как подписанные переходы. Это views тех же screens/actions, а не второй независимый граф. Геометрия карты не меняет положение контролов на экранных листах.

## 15. Диаграммы числового сравнения

### 15.1. Обязательный минимальный объём

**CHART-01.** Для замыкания всего комплекта реализовать компактный профиль CHART со столбчатой и горизонтальной линейчатой диаграммой. Pie, radar, scatter, временные ряды, формулы таблиц и универсальная аналитика не нужны. Для D00 достаточно одной серии экспертных оценок, но модель должна поддерживать несколько серий с группировкой.

| Тип | Поля | Смысл |
| --- | --- | --- |
| `plot` | `kind=column\|bar`, `unit`, `minimum=0`, `maximum`, `decimals=0..6`, `showValues=true`, `sourceNote` | Диаграмма |
| `category` | `owner` plot; `order` | Категория/аналог |
| `series` | `owner` plot; `order` | Ряд |
| `value` | `owner` series; `category`; `number` либо `missing=true` | Одно наблюдение |
| `diagram` | `type=chart`, `plot` обяз. | Лист |
| `view` | один view plot на листе | Отрисовка осей, серий и легенды |

**CHART-02.** Ноль и отсутствующее значение различаются. Дубли series/category блокируются. Все числа конечные; экспоненциальную запись пользователь вводит как текст в кавычках, если общий лексер её не принимает, и декодер числового поля проверяет её целиком. Для первого интерфейса достаточно обычной десятичной формы с точкой в коде; локализованная форма ввода нормализуется без изменения значения.

**CHART-03.** Для bar/column базовая ось включает ноль. Отрицательные значения допускаются и рисуются относительно нуля. Указанный диапазон не должен скрывать наблюдения; либо отклонить настройку, либо явно показать обрезку, но для отчётного экспорта применяется полный диапазон. Округление отображения не округляет сохранённые данные.

**CHART-04.** UI: таблица категорий/серий/значений, перестановка, подпись оси и единицы, источник данных, переключение ориентации, legend/подписи. Перетаскивание столбца не меняет числовое значение; значения правятся в таблице или коде. Цвета и размеры — layout; подпись и число — модель.

```text
chart comparison "Сравнение аналогов"
plot scores "Средняя экспертная оценка" kind=column unit=балл minimum=0 maximum=5 decimals=1 showValues=true sourceNote="Демонстрационный пример языка"
diagram main Сравнение type=chart plot=scores
category a "Аналог A" owner=scores order=0
category b "Аналог B" owner=scores order=1
series average "Средняя оценка" owner=scores order=0
value va "" owner=average category=a number=3.4
value vb "" owner=average category=b number=4.1
view plot_v "" diagram=main element=scores
```

Числа примера иллюстрируют синтаксис, а не подменяют экспертные оценки РОП. При переносе D00 использовать исходные значения комплекта и сохранить их происхождение; не считывать высоты столбцов вместо имеющихся чисел.

**CHART-AC.** D00 воспроизводится из числовых данных. Изменение числа через код и таблицу даёт одинаковый результат. Пустое значение не превращается в ноль; при экспорте видны категории, шкала, единица и источник/примечание.

Нельзя считать написанное внутри label «PK» или «component» автоматически достоверной типизированной моделью. Перенос выполняется через контролируемый конвертер/мастер с выбором нотации и предметным сопоставлением.

**MIG-03.** Обязательный путь конвертера: прочитать известную схему JSON → инвентаризировать элементы/связи → предложить соответствие целевым типам → вывести неоднозначности → построить новый документ штатными командами → validate → preview → сохранить `.omni` в новый путь. Исходный файл не перезаписывается. Успешность конвертации не определяется только тем, что JSON.parse завершился без ошибки.

**MIG-04.** Для ERD главным структурным источником является `База_данных/model.json` с проверкой по `schema.sql`; пять SVG не содержат всей БД. Поле `ref` в старом JSON не гарантирует полного FK: ссылки и составные ограничения также могут быть записаны в `rule`/`constraints`, индексы находятся в корневом `indexes`. Конвертер обязан перечислить все распознанные и нераспознанные ограничения и индексы. Если SQL конфликтует с model.json — показать конкретное расхождение; не выбирать молча.

**MIG-05.** Для двух Sequence использовать существующие UML-механизмы occurrence/message/fragment и сохранить порядок, ветвления, ожидания и ответы. Нельзя переносить только lifeline и сплошные стрелки, теряя асинхронность, alt/loop и причины повторов. После переноса сверить сценарии с текстом ПР8.

**MIG-06.** Каркасы переносить как widget/tableColumn/row/cell. Превращение целого экрана в один imagePlaceholder не засчитывается. Кодирование переносить как сегменты; Function Tree — как parent/order; Component/Activity/Deployment — как соответствующие UML-элементы.

**MIG-07.** По каждому рисунку создать запись происхождения: исходный файл/ID, целевой `.omni`, diagram ID, число перенесённых элементов/связей, нерешённые неоднозначности, статус ручной сверки. Нельзя объявлять пакет полностью перенесённым при хотя бы одной необъяснённой потере. Утилита конвертации — инструмент миграции, не обход запрета на автоматизированные тесты; её запуск не называть проверкой поведения UI.

### 16.2. Сохранение, версия и восстановление

**STORE-01.** `encodeProject`/`decodeProject` — единая граница чтения/записи. Ручной UI, генератор примеров и импорт проходят одинаковые валидаторы. Не создавать «облегчённый режим сохранения» для сгенерированных файлов.

**STORE-02.** Новые поля сохраняются без усечения. Неизвестный notation/новая версия блокируют открытие с понятным сообщением; текущий документ остаётся. Миграция UML v1→v2 сохраняет исходный draft буквально, а source и модель преобразует согласованно. Новые profile-specific defaults не должны незаметно менять смысл прежних четырёх видов.

**STORE-03.** Атомарная запись, recovery, несколько вкладок и внешнее изменение файла используют существующий desktop-контракт. Восстановление сеанса не записывает recovery поверх исходного проекта автоматически. Ошибка экспорта не помечает проект сохранённым.

**STORE-04.** Импорт изображения/SVG как проекта, XML/BPMN XML, XMI и сторонние языки в этой поставке запрещены. SVG-примитивы внутри существующего renderer допустимы как способ рисования; это не разрешает XML-обмен файлами. Внешний SVG-экспорт в ТЗ не включается.

### 16.3. Экспорт для отчётов

**EXPORT-01.** Сохранить существующий PNG и добавить выбор активного листа, выделенной области, набора листов и всех листов документа. Для нескольких документов — пакетная команда по выбранным открытым проектам, без автоматического экспорта неизвестных файлов с диска.

**EXPORT-02.** Диалог: имя/каталог, PNG либо PDF, белый/прозрачный фон для PNG, масштаб или целевой размер, включение заголовка/легенды, отступ, A4/A3/пользовательская страница, ориентация. Не экспортировать сетку, handles, выделение, панель свойств и диагностические подсветки по умолчанию. IDEF0 сохраняет свой лист/штамп, остальные нотации используют границы содержимого или явно заданную страницу.

**EXPORT-03.** Экспорт должен строиться по полной принятой сцене, включая объекты за текущим viewport. Нельзя обрезать модель пределами видимого окна. Пользовательские pan/zoom/выбор и текущая история после экспорта остаются прежними. Невидимый/свёрнутый контент экспортируется согласно выбранному режиму, который указан в preview.

**EXPORT-04.** PDF собирается в заданном порядке листов, с корректной кириллицей и читаемыми линиями. Предпочтителен векторный результат штатного рендера/печати без XML-промежуточного файла. Если конкретный элемент растрируется, это документируется; не называть весь PDF векторным без проверки. Текст и стрелки не должны пересекать границу страницы без режима постерной разбивки.

**EXPORT-05.** Для больших схем предложить: fit на одну страницу, несколько страниц с перекрытием либо крупный формат. Preview сообщает о слишком мелком тексте. Автоматическое уменьшение 29 таблиц до нечитаемой A4 не считается успешным экспортом; пользователь может выбрать пять подготовленных представлений.

**EXPORT-06.** Пакет даёт стабильные имена `номер_название`, отчёт по каждому файлу и причину отказа. Одинаковые названия разрешаются суффиксами без перезаписи ранее существующих файлов. Отмена останавливает оставшиеся операции; уже созданные результаты перечисляются. Повторный экспорт не удаляет чужие файлы каталога.

**EXPORT-07.** Чёрно-белый профиль обязателен: смысл различается формой, наконечником, линией и текстом, а не только цветом. Шрифты выбираются из доступных в приложении; отсутствующий шрифт заменяется с уведомлением в preview. В изображении не допускаются обрезанные строки таблиц, потерянные FK, исчезнувшие pins и стрелки неправильного направления.

### 17.3. Граница данных и исполнения

**NFR-10.** Формулы, guard, SQL default/CHECK, настройки развёртывания, текст widgets и имена файлов — данные. Не использовать eval, Function, shell execution, загрузку скриптов или сетевой запрос на основании содержимого диаграммы.

**NFR-12.** Все шаблоны используют демонстрационные значения, без API-ключей, реальных паролей и служебных токенов. ERD хранит колонку password_hash как элемент модели, не значения паролей. Вариант ООО «Юкомс» не означает авторизации на доступ к реальным сервисам предприятия.

### 18.4. Definition of Done для ИИ-агента

Этап завершён только при одновременном выполнении пунктов:

- Предметные элементы и отношения типизированы; каждый обязательный параметр доступен в UI и собственном языке.
- Все ручные операции проходят один и тот же путь транзакции/валидации; проверки не обходятся генератором или импортом.
- Draft/source/model/layout не расходятся; удаление, копирование, владельцы, история и миграции обработаны.
- Есть открываемый `.omni` из варианта РОП и небольшой отдельный пример пограничных возможностей этапа.
- Обновлены язык, профиль, support matrix, AI_AGENT_GUIDE и журнал. Генерируемая карта актуальна.
- Выполнены разрешённые typecheck/build; их команды и результаты записаны. Ручная приёмка имеет отдельные статусы; неподтверждённое поведение явно перечислено.
- В коде нет заглушек/TODO вместо требований этого этапа, молчаливого отбрасывания полей и кнопок без действий.

Если UI-приёмка запрещена, корректный статус: «реализовано в коде, сборка проверена, ручная приёмка не выполнена». Это не окончательное подтверждение готовности редактора.

### 18.5. Артефакты поставки

1. Код новых адаптеров и расширенного UML в существующем репозитории.
2. Актуальные собственные схемы `.omni` в `examples/`, без альтернативных старых расширений для новых файлов.
3. Документация языка и правил с ID диагностики и границами профилей.
4. Матрица реализации требований и отдельная матрица ручной приёмки.
5. Конвертер подготовленных заготовок с отчётом потерь/неоднозначностей.
6. Перенесённый комплект РОП с реестром diagram ID и 38 экспортированными рисунками; исходные документы сохраняются.
7. Известные ограничения, список непокрытых стандартных возможностей и инструкция следующему агенту.

Формат краткого отчёта исполнителя: «Этапы и ID → изменённое поведение → файлы/примеры → выполненные проверки → непроверенное/оставшееся → следующий шаг». Не перечислять typecheck как тестирование UI.

### 20.2. Первичные внешние источники

- [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/About-UML) и [нормативный PDF](https://www.omg.org/spec/UML/2.5.1/PDF): интерфейсы/структура §10–11, Activity/Action §15–16, Deployment §19. Полный PDF доступен в локальной исследовательской копии проекта; проверены относящиеся к ТЗ фрагменты. Требования этого документа задают ограниченный реализуемый профиль, не заменяют стандарт.

- [ISO 5807:1985, карточка стандарта](https://www.iso.org/standard/11955.html): ориентир области алгоритмических схем. Полный текст не исследован в этой задаче, поэтому FLOWCHART определён как локальный профиль без заявления о полном соответствии ISO/ГОСТ.

### 20.3. Принятые проектные решения

| Решение | Основание/статус |
| --- | --- |
| ERD — отдельная нотация, не набор UML Class с метками PK | Нужна самостоятельная реляционная семантика и физические ограничения |
| Логическая/физическая ERD в первой версии имеют соответствие 1:1 | Сокращает неоднозначность и покрывает подготовленную БД; это локальное ограничение |
| UML расширяется в одном документе | Переиспользуются component/classifier/interface и независимые views |
| Flowchart не является режимом BPMN/Activity | Разные значения узлов и допустимых переходов |
| Дерево использует parent как единственный источник иерархии | Нельзя рассинхронизировать parent и отдельно хранимую стрелку |
| Схема кодирования — типизированный codePattern внутри SCHEME | Достаточно структуры сегментов, не требуется отдельный универсальный язык кодов |
| Каркасы и Chart — небольшие предметные редакторы | Покрывают оставшиеся рисунки без превращения приложения в офисный пакет |
| SQL только генерируется, выражения не исполняются | Редактор моделей не должен менять рабочую БД |
| PNG/PDF и пакетный экспорт обязательны | Рисунки предназначены для учебного отчёта и должны быть читаемы вне приложения |
| Семь остальных отсутствующих UML-видов за границами РОП | Не относятся к согласованному списку и не должны получать ложную отметку готовности |

Если агент обнаружит несовместимость предлагаемого DSL с текущим общим механизмом, он должен расширить общий механизм без изменения базовой формы NS-TEXT-2. Нельзя решать проблему введением второго языка, отдельного пользовательского canvas или потери модельных свойств.
