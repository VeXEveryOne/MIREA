Результат работы: 
1. Описание процесса AS-IS 
В исходной учебной модели покупатель направляет пожелания менеджеру в 
форме переписки и файлов. Менеджер вручную передаёт материалы дизайнеру. 
Концепция и спецификация последовательно согласуются с покупателем, 
проектным отделом и отделом строительства. При замечаниях обновлённые файлы 
рассылаются повторно. После согласования дизайнер или менеджер вручную 
передаёт перечень материалов в снабжение. 
Проблемы AS-IS: отсутствует единый номер и статус заявки; возможна 
работа с устаревшей версией концепции; реквизиты повторно вводятся в разные 
документы; замечания не имеют общего журнала; контроль сроков и полноты 
закупочной потребности выполняется вручную.

менее 100 000 заявок без изменения

5. Вывод 
Спроектированный TO-BE процесс переводит работу с заявкой в единую 
систему: устраняет разрозненность файлов, фиксирует версии и решения, 
контролирует маршрут согласования и создаёт полную закупочную потребность 
только по утверждённой концепции. Модели и сценарии служат основой для 
дальнейшего проектирования данных и интерфейсов.

 концепция может содержать несколько версий - 1:N; 
 каждая версия концепции может содержать несколько файлов - 1:N; 
 одной версии соответствует спецификация - 1:1; 
 спецификация содержит несколько позиций - 1:N; 
 один материал может использоваться во множестве спецификаций - 1:N; 
 одна версия концепции может иметь несколько результатов согласования - 
1:N; 
 одна заявка может иметь одну или несколько закупочных потребностей - 
1:N; 
 закупочная потребность содержит несколько позиций - 1:N; 
 для одной заявки может быть создано множество записей журнала действий 
- 1:N; 
 пользователь может получать множество уведомлений - 1:N. 
 один статус закупочной потребности может соответствовать нескольким 
закупочным потребностям — 1:N.

5. Схема кодирования заявки 
Для однозначной идентификации заявки используется код: 
APP-YYYY-NNNNN 
где: 
APP - постоянный префикс заявки; 
YYYY - год регистрации; 
NNNNN - порядковый номер заявки в пределах года. 
Например: 
APP-2026-00125 
означает заявку №125, зарегистрированную в 2026 году. 
Такой подход соответствует принципу структурированного кодирования, 
описанному в методических материалах: код должен состоять из отдельных 
смысловых частей и иметь однозначные правила формирования.

1. Проектирование инфраструктуры информационной системы 
Ранее для проектируемой системы была определена компонентная 
архитектура, в которой web-интерфейсы обеспечивают доступ пользователей по 
HTTPS, сервис заявок обрабатывает карточки, версии и статусы, сервис 
согласований управляет решениями участников, структурированные данные и 
журнал аудита хранятся в базе данных, а файлы концепций - в отдельном файловом 
хранилище.  
С учётом данной архитектуры предлагается использовать клиент-серверную 
инфраструктуру. Пользователи работают с системой через браузер со своих 
рабочих станций. Запросы передаются по сети Интернет с использованием HTTPS 
и проходят через межсетевой экран. Далее запрос поступает на web-сервер, 
который перенаправляет его серверу приложений. 
Сервер приложений реализует бизнес-логику системы: регистрацию заявок, 
работу с концепциями и версиями, согласование, формирование закупочной 
потребности, аналитику и управление правами доступа. 
Для хранения структурированных данных используется отдельный сервер 
PostgreSQL. Файлы проектов и концепций размещаются в файловом хранилище. 
Для обеспечения восстановления информации предусматривается резервное 
хранилище. 
Такое разделение соответствует уже установленным требованиям проекта: 
полная резервная копия базы данных должна создаваться не реже одного раза в 
сутки, а система должна поддерживать хранение не менее 100 000 заявок.

7. Выбор системы управления базами данных

Основными причинами выбора являются: 
 отсутствие необходимости приобретения коммерческой лицензии; 
 развитая поддержка реляционной модели данных; 
 обеспечение ссылочной целостности; 
 поддержка транзакций;

 возможность дальнейшего масштабирования. 
Выбор реляционной СУБД соответствует структуре проектируемой 
системы. В ней присутствует большое количество связанных сущностей:

Проектируемая информационная система реализована как web-приложение с 
серверной частью на Java и Spring Boot. Для хранения структурированных данных 
используется PostgreSQL, а файлы концепций размещаются в отдельном файловом 
хранилище. В процессе обработки заявки также предусмотрено взаимодействие 
отдела снабжения с поставщиками. 
В предыдущих работах для системы были определены функции хранения 
проектных файлов и взаимодействия с поставщиками при формировании 
закупочной потребности.  
Для моделирования выбраны два интеграционных сценария: 
  

=== СТРАНИЦА 81 ===
81 
 
Сценарий 1 - загрузка файла концепции в выделенное файловое 
хранилище. 
Участники: 
 дизайнер; 
 web-интерфейс; 
 Spring Boot-приложение; 
 PostgreSQL; 
 файловое хранилище. 
Назначение сценария - обеспечить сохранение файлов концепции в 
выделенном файловом хранилище отдельно от базы данных. В PostgreSQL 
сохраняются только метаданные файла и ссылка на объект. 
 
Сценарий 2 - передача закупочной потребности внешнему поставщику. 
Участники: 
 сотрудник снабжения; 
 web-интерфейс; 
 Spring Boot-приложение; 
 PostgreSQL; 
 внешняя информационная система поставщика. 
Назначение сценария - передать сформированную закупочную потребность 
поставщику и получить результат обработки. 
Для обоих сценариев взаимодействие осуществляется по защищённому 
соединению HTTPS. Для структурированных сообщений используется JSON. 
Методические материалы требуют указывать протоколы и форматы именно на 
таком уровне, без разработки собственной API-спецификации.

2. Интеграционный сценарий загрузки файла концепции 
Дизайнер формирует новую версию концепции и прикрепляет проектный 
файл. Web-интерфейс передаёт файл серверному приложению. Spring Boot 
проверяет права пользователя, тип и размер файла, после чего передаёт файл в 
файловое хранилище. 
При успешном сохранении файловое хранилище возвращает идентификатор 
или путь к объекту. После этого серверное приложение сохраняет сведения о файле 
в таблице project_files. 
Если файловое хранилище недоступно, сведения о файле в базе данных не 
создаются, а пользователь получает сообщение об ошибке.

3. Интеграционный сценарий передачи закупочной потребности 
После завершения всех обязательных согласований система формирует

Возможны три основных результата: 
 закупочная потребность принята; 
 закупочная потребность отклонена; 
 внешний сервис недоступен.

4. Разграничение прав пользователей 
В проектируемой системе используется ролевая модель управления доступом 
- RBAC. 
В рамках проектируемой информационной системы каждому пользователю 
назначается одна основная роль, определяющая доступный набор операций. Роль 
пользователя хранится в поле users.role_code 
В ранее разработанном кодификаторе были определены следующие роли: 
 CUS - покупатель; 
 MAN - менеджер; 
 DES - дизайнер; 
 PRO - проектный отдел; 
 CON - отдел строительства; 
 SUP - снабжение; 
 ANA - аналитик; 
 ADM - администратор.  
  

=== СТРАНИЦА 85 ===

пользователю. Методические указания требуют придерживаться принципа 
минимальных привилегий: по умолчанию операция запрещена и разрешается

6. Реализация разграничения доступа 
В Java-приложении контроль доступа предлагается реализовать с 
использованием Spring Security. 
Проверка выполняется на нескольких уровнях: 
Уровень web-интерфейса. Пользователю отображаются только доступные 
ему разделы и действия. 
Уровень REST-контроллеров. Перед выполнением операции проверяется 
наличие необходимой роли. 
Например: 
@PreAuthorize("hasRole('DES')") 
для операций дизайнера. 
Для операций, доступных нескольким ролям: 
@PreAuthorize("hasAnyRole('MAN', 'ADM')") 
Уровень бизнес-логики. Дополнительно проверяется принадлежность 
объекта пользователю. 
Например, одного наличия роли CUS недостаточно для просмотра любой 
заявки: должно выполняться условие: 
application.customer_id = current_user.user_id 
Это обеспечивает строковое ограничение доступа.

8. Защита интеграционных взаимодействий 
Для взаимодействия Spring Boot с внешними сервисами применяются 
следующие правила: 
Передача данных осуществляется только по HTTPS. Незашифрованное 
HTTP-соединение для внешних интеграций не используется. 
Внешний сервис должен проходить аутентификацию. Для 
межсистемного взаимодействия применяются отдельные технические учётные 
данные или токены доступа. 
Секреты не хранятся в исходном коде приложения. Они передаются 
через переменные окружения или защищённое конфигурационное хранилище. 
Входящие и исходящие данные проверяются. Ответ внешнего сервиса не 
считается доверенным автоматически. 
Ошибки внешнего сервиса обрабатываются отдельно. Недоступность 
поставщика или файлового хранилища не должна приводить к повреждению 
внутренних данных. 
Интеграционные операции регистрируются в журнале. Для критичных 
действий сохраняются время запроса, результат и пользователь, инициировавший 
операцию.

Вывод 
В ходе выполнения практического занятия были определены основные 
интеграционные взаимодействия проектируемой информационной системы. 
Для сценариев загрузки проектных файлов и передачи закупочной 
потребности внешнему поставщику разработаны диаграммы последовательности, 
отображающие участников, порядок обмена сообщениями, используемые 
протоколы и обработку возможных ошибок. 
Для управления доступом сформирована ролевая модель RBAC, 
включающая роли покупателя, менеджера, дизайнера, проектного отдела, отдела 
строительства, снабжения, аналитика и администратора. Для каждой роли 
определены доступные ресурсы, операции и ограничения. 
Определены меры информационной безопасности, включающие 
аутентификацию, авторизацию на основе Spring Security, защищённый обмен по 
HTTPS, серверную валидацию данных, аудит действий пользователей, безопасное 
хранение секретов и резервное копирование. 
Разработанные решения обеспечивают контролируемое взаимодействие 
внутренних компонентов системы с внешними сервисами и ограничивают доступ 
пользователей в соответствии с их функциональными обязанностями.
