 Рисунок 4 — Sequence Diagram RBAC (Role-Based Access Control) — модель управления доступом, в которой права назначаются не пользователям напрямую, а ролям. Пользователь получает доступ, становясь участником одной или нескольких ролей. Базовая матрица фиксирует соответствие: Роль × Ресурс × Операция (CRUDX), где операции: Create/Read/Update/Delete/Execute. Ключевые понятия: 1. Роль — набор разрешений, отражающий служебные обязанности (например, Пользователь, Менеджер, Администратор). 2. Ресурс — объект доступа (сущность системы, экран, API-эндпоинт, отчёт, очередь сообщений). 3. Операция — допустимое действие над ресурсом: C (создать), R (просмотреть), U (изменить), D (удалить), X (выполнить/запуск). 4. Ограничение — условие на уровень строки/поля/контекста (например, «только свои записи», «только в пределах

подразделения»). 5. Принцип наименьших привилегий — по умолчанию запрет, разрешается только необходимый минимум. Виды ограничений: 1. Объектный уровень: доступ к конкретным ресурсам/экрану/эндпоинту. 2. Строковый уровень (Row-Level): фильтры по владельцу, подразделению, организации/тенанту. 3. Полевой уровень: запрет/только чтение отдельных атрибутов (например, скрыть зарплату). 4. Временные/контекстные: доступ в рабочее время, из доверенной сети и т. п. 5. Разделение обязанностей (SoD): несовместимые роли не должны назначаться одному пользователю (например, Создаёт платёж ≠ Утверждает платёж). Порядок разработки RBAC: 1. Определить ресурсы (сущности, отчёты, функции, эндпоинты). 2. Сформировать операции для каждого ресурса (CRUDX) и их смысл. 3. Описать роли (по бизнес-функциям), при необходимости ввести иерархию ролей. 4. Заполнить матрицу ролей и операций; для нестандартных случаев указать ограничения/фильтры. 5. Связать матрицу с механизмом исполнения: • в приложении — проверки на экранах/кнопках и при вызове сервисов; • в API — политики на эндпоинтах (scope/claim → разрешения); • в БД — роли/гранты, политики RLS (Row-Level Security). 6.
