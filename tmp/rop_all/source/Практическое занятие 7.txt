Цель занятия: разработать физическую модель данных и сформировать схему развертывания (Deployment Diagram). Постановка задачи: 1. Разработать физическую модель базы данных (с указанием таблиц, типов данных, размеров, ограничений). 2. Составить табличное описание атрибутов каждой таблицы (тип данных, размерность, требования, ограничения). 3. Построить Deployment Diagram (диаграмму развертывания), отражающую размещение программных компонентов на физических и виртуальных серверах. 4. Проверить согласованность физической модели с ранее построенной логической моделью данных. 5. Использовать инструменты (PlantUML, Draw.io, текстовый и табличный редактор) для построения схем и описания атрибутов. Теоретический вспомогательный материал Физическая модель базы данных — это описание структуры БД на уровне реализации в выбранной СУБД. Она фиксирует реальные таблицы, поля и их типы, индексы, ключи и ограничения, правила хранения и доступов. Физическая модель является результатом детализации логической модели (ERD) и служит основой для генерации DDL‑скриптов. Далее указано, что должна включать в себя физическая модель БД. Таблицы и поля содержат наименования, назначение, состав полей. Типы данных содержат конкретные для СУБД (например, INTEGER, NUMERIC(12,2), V ARCHAR(100), DATE/TIMESTAMP, BOOLEAN, JSONB в PostgreSQL) типы. Ограничения целостности: 1. Первичный ключ (PK). 2. Внешние ключи (FK).

3. Уникальность (UNIQUE). 4. Обязательность (NOT NULL). 5. Проверочные ограничения (CHECK). 6. Значения по умолчанию (DEFAULT). Индексы: состав, тип (B‑tree, hash, полнотекстовые), уникальность, покрывающие/частичные, кластерные/некластерные. Нормализация/денормализация: принятые решения для производительности и простоты запросов. Хранение и производительность: партиционирование, автогенерация ключей (IDENTITY/SEQUENCE), материализованные представления, параметры автозаполнения/автоинкремента. Коллация и кодировка: правила сравнения строк и набор символов (например, UTF‑8, ru_RU.utf8). Безопасность и доступы: роли, права (GRANT), политики строкового уровня (Row‑Level Security). Аудит и служебные поля: created_at, updated_at, created_by, is_deleted (мягкое удаление). Именование и комментарии: единые префиксы/постфиксы, комментарии к объектам. Переход от ERD к физической модели осуществляется следующим образом: 1. Каждая сущность → отдельная таблица. 2. Каждый атрибут → поле с типом и ограничениями. Каждая связь: 1. 1:N — внешний ключ в стороне «многие». 2. M:N — отдельная таблица‑связка с двумя внешними ключами (и, как правило, составным PK). 3. 1:1 — один к одному. Используется для фиксирования среды исполнения системы: серверов, контейнеров, виртуальных машин, мобильных устройств, сетевых связей, протоколов. Основные элементы: 1. Node (узел) — вычислительный ресурс, на котором исполняется ПО. Варианты: физическое устройство (Device: сервер, маршрутизатор), виртуальная машина, контейнер, облачный сервис, мобильное устройство. 2. Execution Environment (EE) — среда исполнения внутри узла: JVM, .NET CLR, контейнер Docker, сервер приложений. 3. Artifact (артефакт) — развёртываемый файл/единица поставки: исполняемый модуль, JAR/WAR, контейнерный образ, конфигурация. 4. Communication Path — соединение между узлами (указывают протоколы/порты: HTTP/HTTPS, gRPC, JDBC). 5. Deployment — связь «артефакт → узел/среда исполнения», обозначающая, где и как развернут артефакт. 6. Стереотипы — уточнения роли: «web-server», «db-server», «message-broker», «cache», «gateway» и т. п. Пример данной диаграммы представлен на Рисунке 3.
